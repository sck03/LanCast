# 01 产品范围与技术决策

## 1. 产品目标

局域网内将Windows电脑和Android手机的屏幕、单个应用画面或视频文件投到电视/投影仪，优先画质、音画同步、稳定性，并覆盖禁止安装第三方App的电视。不需要公网账号或云端中继。

v1.0发送目标：Windows10 22H2/Windows11 x64、Android10/API29+。自有接收目标：可安装App的Android5/API21+设备，按Standard/Legacy构建。iOS/iPadOS16+在v1.2增加自有发送App；macOS/Linux/tvOS原生客户端不进入1.x。

## 2. 三种能力同时规划、分别验收

| 用户任务 | 路由 | 编码与容器 | 需要自有接收App | 用途 |
|---|---|---|---|---|
| 屏幕/应用交互镜像 | WebRTC | H.264 + Opus，经RTP/SRTP | 是 | 优先低延迟与可控诊断 |
| 受限电视桌面/PPT | DLNA桌面直播 | H.264 + AAC-LC，连续MPEG-TS经HTTP | 否，但电视须支持该直播形式 | 兼容演示，按实际电视延迟分级 |
| 现有视频文件 | 自有直放或DLNA文件 | MP4/H.264/AAC原文件 | 自有直放需要，DLNA不需要 | 保留画质，减少重编码/耗电 |

DLNA桌面直播是首版功能，不再仅列为研究候选。它不要求电视解析PPT文件：发送端运行PPT并采集放映画面，电视播放实时生成的视频。不能把“发现DLNA设备”或“MP4可播”当作连续TS直播已经兼容。

一个发送端一次只激活一条媒体路由、一个接收端一次只显示一个活动来源。切换来源/协议必须显式停止旧会话、确认新来源；不静默扩大采集范围。

## 3. 设备接入原则

可以安装自有App的设备优先自有通道。不能安装但有DLNA的设备进入兼容直播/文件通道；未知直播能力由用户主动启动合成内容测试，测试成功后才记录设备档案。

只有AirPlay/Miracast的设备可以使用其系统入口，产品提供准确说明但不冒充我们的媒体会话。只有Google Cast时1.x不直接接入，用户可使用已有官方Cast应用。无共同协议又不能安装时需要外接允许安装接收App的盒子；不得宣称所有电视都能无额外硬件镜像。

系统版本、厂商安装政策、协议能力、codec能力、实测性能分开建模。禁止安装App是中国电视必须覆盖的场景，不根据品牌或“Android”字样推断可侧载，不声称掌握受限设备的市场比例。

## 4. 编程语言与实现选择

| 部分 | 决定 | 理由 |
|---|---|---|
| Android应用 | Kotlin + Views/XML | 原生权限与生命周期、空安全、维护性；不要求Compose运行时 |
| 控制/发现/会话/HTTP/UPnP | Rust | 严格类型、内存安全、跨平台复用；不负责处理逐帧像素 |
| 媒体与Windows平台适配 | C++20 + 系统API | GPU资源、Media Foundation、libwebrtc接口与成熟媒体库接入 |
| Windows UI | 轻量Win32原生界面 | 不带浏览器或托管UI运行时；功能聚焦设备、来源、状态与控制 |
| Apple后续 | Swift + 必要Objective-C++桥 | ReplayKit、平台音频/视频权限和扩展生命周期 |

不使用Go作为第二套控制实现，不维护Java版Android业务，不把全部功能写进一个C++大模块。Kotlin与Java的选择不是视频吞吐量的决定因素；主要性能来自硬件编解码、GPU路径、队列和调度。

## 5. 媒体与包体决策

实时镜像复用libwebrtc，源版本固定、只注册H.264/Opus能力，裁掉未用功能与工具。Windows硬件H.264使用Media Foundation，Android使用MediaCodec。平台适配器和libwebrtc C++接口在同一受控工具链内构建，通过窄C ABI与外部应用交互。

DLNA直播不复用RTP字节，不把Opus装入TS。使用原始捕获数据选择H.264/AAC编码，FFmpeg只启用MPEG-TS封装及其必要基础依赖。首版不带FFmpeg命令行、通用转码服务器、大批软件codec或网络协议。

不使用现有GStreamer/WinUI/.NET代码作为兼容约束；不引入其完整分发包。这样减少运行时和插件范围，但需要自己完成系统媒体适配、设备缺陷处理与发布测试。小包体不能靠省略必要的错误处理和测试实现。

Standard接收API23+用Media3当前固定版本；Legacy主要服务API21/22，用系统MediaPlayer，功能限定MP4直放与基本控制。Legacy不绑定停止升级的旧Media3；系统播放器缺陷通过设备档案限制，不能靠强制改minSdk掩盖。

## 6. 范围限制与后续扩展

v1.0不承诺4K/HDR、HEVC/AV1、远程操控、游戏级延迟、多路拼屏、字幕全格式、HLS/DASH、视频转码、受保护网页内容提取、云投屏。音频采集尊重操作系统和应用策略，不能录到时清楚说明，不自动改录麦克风。

未来新codec、协议、播放器、平台以适配模块接入，必须声明能力/许可证/版本/测试矩阵。不先写一个可动态加载任意第三方代码的“万能插件系统”；v1使用编译期注册和功能裁剪，保持可维护性与可审核性。

## 7. 核心决策记录

| 编号 | 决定 | 触发重新评审的条件 |
|---|---|---|
| D01 | 三条首版通路，DLNA直播正式实现 | 目标电视样本证明连续流不可用且没有有价值覆盖 |
| D02 | Kotlin/Rust/C++分工 | 新平台或团队长期维护成本有可量化变化 |
| D03 | 定制libwebrtc + 最小TS封装，避免通用媒体运行时 | 实测原生适配成本/性能不达标，而替代方案满足包体与稳定性门槛 |
| D04 | Standard/Legacy共享核心，播放器实现分开 | 实际API21/22覆盖需求消失或系统播放器无法满足基础验收 |
| D05 | 文件直放优先，镜像不得重复编码已有文件 | 新内容来源只能按合法授权的捕获路径输出 |
| D06 | 模块接口版本化，跨语言不传内部容器 | 接口新增字段超出兼容扩展能力，需要提升major版本 |

重新评审是有证据的工程变更，不允许实现者为了省事在某个模块暗自引入另一套运行时或改变支持承诺。
