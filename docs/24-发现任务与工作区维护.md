# 24 发现、DLNA控制与工作区维护

D20合同，D31更新至0.6.16 / 24，2026-11-07。实际提交、Actions结果和清理字节数统一记录在[08](08-实施进度与审阅入口.md)。

## 问题与修改

旧版每次`scan`都会分离一个`spawn_blocking`任务，阻塞等待mDNS结果；`stop`没有取消这些任务。新增回归在旧实现上复现了`stopped`之后约4秒仍收到`devices`事件，重复搜索也可能同时保留多组线程和套接字。DLNA描述请求只有每请求超时：64个地址、8路并发可形成多批等待，描述阶段没有统一截止。

现在每个Engine只拥有一个自有设备搜索任务。新搜索先取消并等待旧任务，停止也等待该任务退出；mDNS改用已有接收通道的异步通知，移除额外阻塞线程和250毫秒定时轮询。守卫负责在正常返回、初始化失败和取消时向mDNS守护线程发送关闭请求；底层库的线程退出仍由其自身执行，没有宣称实现同步线程join。

| 边界 | 当前实现 | 扩展约束 |
|---|---|---|
| Runtime | 编排mDNS/DLNA开始与停止，选择DLNA完成通知 | 网络搜索不占用命令等待路径；停止/关闭优先于待交付的搜索结果 |
| discovery/tasks | `ScanTask<T>`持有任务并等待取消；`DlnaDiscovery`管理设备目录和结果交付 | 新扫描清空旧目录；目录先更新再发事件；已交付结果仍由宿主按`scanGeneration`过滤 |
| mDNS | 异步接收，4秒截止，最多64个已解析设备 | 广播提示不构成信任；完整指纹与配对版本检查保持有效 |
| SSDP / 描述解析 | 最多64个地址、8路HTTP并发，SSDP发送完成后的接收预算4秒、整轮网络等待预算8秒 | 到期保留已解析设备并释放未完成请求；描述大小、来源IP和XML限制继续生效 |
| DLNA结果集合 | 最多64台设备，序列化JSON数组预算96KiB，超限条目跳过 | 计入UTF-8、JSON转义与分隔符；同ID替换先核算新旧差额，超限保留旧条目，较小替换释放预算 |
| dlna/description | 纯设备描述解析，借用XML文本，只解析实际使用的AVTransport端点 | URLBase只取根元素直接子项；控制地址必须非空且仍绑定SSDP来源IP；无关服务不影响发现 |
| dlna/soap | 纯SOAP响应校验、字段长度限制与结构化结果 | 只读取对应动作的直接字段，不拥有网络、事件或Runtime；原文XML和远端诊断不透传宿主 |
| workspace_cleanup | 路径分类、预览、重新核验、删除或移至待手动删除目录 | 与产品运行时分离，仅依赖Python标准库和Git；新增缓存先添加明确规则和保护回归 |

发现协议仍在adapters内；domain/core、媒体路径和C ABI没有增加平台依赖或改变字段。Apple使用系统Bonjour的路径不经过这里的mDNS扫描；共享DLNA能力也没有扩展到Apple UI。D31已将DLNA网络工作移出Runtime命令序列，结果仍由同一个命令拥有者提交。

## D29 描述处理与事件预算

旧实现允许单份描述XML达到512KiB，却将解析后的全部设备无总字节预算地放入128KiB上限的宿主事件。超长名称或多个较大条目会触发`HOST_EVENT_QUEUE_OVERFLOW`并关闭整个Engine。现在`discovery`在保存条目前用`protocol::json_size`计数，不分配临时JSON字符串，超预算设备不进入结果集。96KiB结果预算为事件外壳保留空间；`scan`与`dlna.scan`的`scanGeneration`统一要求无符号64位整数，缺失或类型错误返回`SCAN_GENERATION_REQUIRED`，不回传任意大小的JSON值、不启动网络工作。

旧解析器为所有服务解析URL并分配`Service`，即使无关的厂商诊断服务使用域名地址，也会让有效AVTransport设备整项失败。现在只解析选中的AVTransport，仍拒绝其跨主机、认证信息、片段和非HTTP(S)端点。缺失或空白`controlURL`明确拒绝，不再将描述文档地址当成控制地址；错误嵌套的`URLBase`不参与解析。描述模块不持有网络连接、宿主事件或Runtime状态。

XML继续限制512KiB、8192节点与既有深度，并由解析器的`allow_dtd: false`拒绝DTD；移除每次解析整份XML的大写副本，注释中的`<!DOCTYPE`文字不会被误判成声明。设备字段在XML树内借用，仅最终输出字段分配字符串；删除未使用服务向量及逐服务的前缀格式化，Runtime将解析结果移入设备目录，减少一次完整设备复制。以上为分配路径改进，没有宣称CPU、RSS或实机延迟已测得改善。

## D30 SOAP控制响应与事件边界

旧实现将最大512KiB的SOAP响应原文放进`dlna.state.body.response`，超过128KiB宿主事件限制就会触发`HOST_EVENT_QUEUE_OVERFLOW`并关闭Engine。本轮先用160KiB合法XML复现，再移除原文透传。SOAP Fault的`errorCode`以及XML解析器包含远端名称的诊断也可能过长，现在错误路径同样有界。

Controller仍负责固定AVTransport端点、五秒请求超时和最多512KiB响应读取；`soap::decode`一次解析XML，校验SOAP 1.1 Envelope、唯一Body回复、动作响应名及服务命名空间。状态和URI只从对应响应的直接子项提取，Header、嵌套伪字段、重复字段和错误动作不作为有效结果。XML字节数、节点数、深度与DTD限制继续共用既有解析入口。

当前`dlna.command`的`dlna.state`事件保留`firstFrameMeasured: false`，`body.response`改为以下对象；不保留旧原文字符串回退：

| 动作 | response | 字段预算 |
|---|---|---|
| play / pause / stop / seek | `{"kind":"accepted"}` | 仅代表命令响应通过，不能断言电视画面成功 |
| state | `{"kind":"state","transportState":"PLAYING"}` | 状态文本最多64个UTF-8字节，缺失或空值拒绝 |
| position | `{"kind":"position","relativeTime":"00:12:34","trackDuration":"NOT_IMPLEMENTED"}` | 两个文本各最多32字节；缺失为null，保留UPnP时间和NOT_IMPLEMENTED含义 |

内部`GetMediaInfo`只提取最多8192字节的CurrentURI，用于停止/恢复前检查当前资源；它不进入宿主控制结果。字段预算计算解码后全部文本，包括注释分隔的文本片段，在复制前检查；嵌套元素拒绝。Fault只保留能解析为u16的错误码，其他内容输出`DLNA_SOAP_FAULT: unknown`；XML错误输出固定`DLNA_INVALID_XML`，不附带远端名称。

`GetTransportInfo`和`GetPositionInfo`失败最多再查询一次；加载、播放、暂停、停止和跳转不自动重试，避免超时后重复操作。状态监控和URI检查直接使用同一次解析的结果，不再为字段读取重新构建XML树。XML转义改为一次遍历，避免连续五次replace的临时字符串；无新增运行依赖或平台代码分支。Windows/Android宿主原本只显示指令返回状态，无需解析或保留SOAP。

合成直播示例使用符合SOAP命名空间的模拟电视响应。回归覆盖大元数据的紧凑事件、超长字段/错误码/解析诊断、错误动作/命名空间、重复与嵌套字段、注释分隔文本、位置和URI提取。CPU/RSS、真实电视响应差异和长时间投屏仍需设备验证，代码分配路径减少不等于已测得端到端性能提升。

## D31 DLNA搜索调度与任务所有权

此前`dlna.scan`直接在Runtime命令处理函数里等待网络完成。即使UI异步调用核心，后续配对、连接和路由等普通命令仍需等待最长8秒。回归先在原路径复现：发送搜索后紧接路由查询，2秒内收不到结果。搜索改为独立Tokio任务后，同一测试可以立即处理路由查询；这是控制队列响应的回归证据，不代表电视发现时间或投屏延迟缩短。

`discovery/tasks.rs`统一搜索所有权；`ScanTask<T>`复用先取消、等待退出、再替换的机制，mDNS和DLNA各最多一个任务。`DlnaDiscovery`持有本轮任务、u64扫描代次和设备目录；无需新增线程、无界结果队列或目录互斥锁。`JoinHandle`本身保留至多一份完成结果，在Runtime空闲时参与`select!`。关闭和停止优先；搜索结果就绪后仅提交一次，目录更新和事件发布之间没有异步挂起点。宿主收到`dlna.devices`后可以立即选择对应设备。

新扫描先回收旧任务，再清空目录；未交付的旧结果随任务句柄一同丢弃。`stop`等待搜索任务退出，不发布被取消的结果；已经发布的目录保留，支持停止投屏后重新选择当前设备。完成分支等待可安全中断，其他命令不会导致搜索结果丢失。任务替换/停止即使被外层停止或关闭打断，也仍持有已中止的句柄；后续清理继续等待它退出，避免提前丢弃句柄使旧任务脱离拥有者。

扫描失败统一交付空数组、原扫描代次和固定`DISCOVERY_FAILED`，不透传底层任意错误字符串。64设备、8路描述并发、96KiB结果预算及整轮8秒网络截止继续生效。此修改不保留旧串行搜索路径，也没有增加运行依赖；已在执行中的其他长命令仍可能延后结果交付，后台搜索本身不会阻塞它们。

确定性回归覆盖完成等待反复被取消、目录先于事件可用、已完成旧结果替换、停止时等待退出并丢弃结果、失败后重试及中断停止保留所有权。真实Engine集成测试使用可用私网接口验证普通命令响应；没有私网路由的环境跳过该网络项，任务生命周期回归不依赖网络。

## 构建体积与清理

两个Rust工作区的开发/测试配置采用`debug = "line-tables-only"`和`incremental = false`，保留回溯行号，减少完整调试信息与增量编译缓存。代价是修改后的重编译可能更慢；需要调试局部变量时可显式设置`CARGO_PROFILE_DEV_DEBUG=2`。Release的LTO、代码生成和符号设置未调整。GitHub Rust缓存键加入manifest，开发缓存使用新版本前缀，避免继续恢复旧的完整调试缓存；Apple缓存也包含核心源码输入。

在仓库根目录运行：

```sh
# 默认只预览；JSON适合保存为审阅记录
python scripts/workspace_cleanup.py --include-downloads --json

# 构建、测试及本机产物复核结束后，集中保留以便手动删除
python scripts/workspace_cleanup.py --quarantine --include-downloads --json

# 已明确决定自动删除时使用；与 --quarantine 互斥
python scripts/workspace_cleanup.py --clean --include-downloads --json
```

默认包含Rust target、已知CMake/Gradle/Swift构建目录、Python字节码和历史合成解码中间产物。`--include-downloads`额外包含已知下载缓存，如Actions产物、FFmpeg源码归档和格式工具。路径规则位于脚本顶部；不递归删除整个`.cache`，未知缓存、原始硬件样本和外部研究仓库保留；可能由用户提供的RTC AAR/Framework不自动删除。

`--quarantine`复用删除模式的整份预检及逐项重新核验，拒绝重叠路径，并把生成物重命名到Git忽略的`.manual-delete/<UTC时间>-<随机标识>/`，保留原相对目录。`manifest.json`记录每项原路径、字节数、指纹及移动状态；占用或权限错误会停止操作并记录失败，已移动项保留，未移动项留在原地。只使用同文件系统重命名，不回退为复制后删除。目标链接、跟踪文件和未忽略目标均拒绝；新一轮不会覆盖旧清单。

移动模式报告`moved_bytes`，`removed_bytes`保持0；实际释放空间需要手动删除该目录。待删除目录不参与后续自动清理，也不得提交到GitHub。可按清单将所需文件移回原位置，恢复前先检查该位置是否已有新构建结果。

删除前要求目标位于当前Git工作区内、符合Git忽略规则且不包含跟踪文件；拒绝链接/Windows junction、嵌套Git仓库、签名材料和特殊文件。先核验整份计划，再逐个重新读取Git索引和文件元数据，发现变化就停止。执行时应结束构建和使用这些目录的工具；该脚本没有跨进程文件锁，不支持与构建并行清理。读取失败或删除失败会报错，不将未删除文件记为已释放。

源码、锁文件、许可证、vendored协议实现和已提交的验证摘要是有效项目内容。初始设计存档和硬件采集原件也有追溯用途；空间回收以生成物为主。工作区体积、安装包体积、运行时内存分别测量。

## 验证与剩余验收

新增自动化覆盖重复搜索先回收旧任务、任务拥有者销毁、停止后无迟到搜索事件、描述截止保留部分结果并取消未完成工作、过期请求不再启动。清理回归覆盖只读预览、保留源码/未知缓存、重复执行、跟踪文件、并发修改、索引变化、嵌套仓库、签名材料、越界路径和Windows junction/POSIX链接。

D29回归先在旧实现复现超大描述、无关服务和空控制地址三个失败，再覆盖转义后的集合预算、同ID替换和名额上限、URLBase作用域、跨主机端点、DTD/节点/深度限制及错误扫描代次。使用真实Engine事件队列确认错误输入不会关闭核心。

继续通过仓库`github-ci.py`调用和审阅八个GitHub工作流，完整平台产物由现有构建/校验脚本生成。真实多网卡切换、密集设备搜索、电视慢响应，以及CPU/RSS、音画同步、端到端延迟和两小时长稳仍需设备验收；本轮自动化和磁盘回收不替代这些结果。
