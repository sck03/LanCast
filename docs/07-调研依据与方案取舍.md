# 07 调研依据与方案取舍

调研日期：2026-10-03。检查了公开文档、关键源码、构建文件与部分依赖元数据。未做商用品性能横评，也未在用户电视运行参考项目；不把厂商宣传或上游自动化测试当作本项目实测。

## 1. 开源实现与本设计采用点

| 项目 | 可核实内容 | 采用/不采用 |
|---|---|---|
| dlna-screen-cast | WGC窗口/桌面→H.264/AAC→MPEG-TS→持续HTTP，UPnP SetURI/Play，关键帧与缓冲处理 | 采用路线和验证思路；不继承其C#/.NET界面、完整构建/运行时 |
| Sunshine | GPU捕获、硬件编码、WASAPI与输出设备变化 | 借鉴系统适配与诊断；不复制GPL实现，不引入第二套GameStream主协议 |
| Moonlight Android | API21兼容、硬解缺陷处理、低延迟配置、帧调度 | 借鉴设备矩阵与帧调度方法；不复制GPL代码 |
| scrcpy | Android采集与编码，音频路径使用ADB/shell能力 | 借鉴媒体处理；普通App不继承shell权限、REMOTE_SUBMIX或开发者模式前提 |
| libwebrtc | RTP/RTCP、SRTP、拥塞、抖动缓冲、同步与平台接入 | Android实时媒体基础；当前固定上游AAR，定制源构建仍未完成 |
| libdatachannel | 独立ICE/DTLS/SRTP、RTP/RTCP传输 | D08的Windows RTC传输，硬件编码由平台模块提供 |
| UxPlay | 通过Legacy Protocol兼容AirPlay 2；C/C++协议核心与渲染分开，核心已使用RTSP | D15的C/C++镜像优先参考和兼容路线，不代替现代AP2验收；见18/19 |
| [rairplay](https://github.com/r4v3n6101/rairplay) | Rust库带C代码，HomeKit/Legacy配对与音视频接口，非现成Android接收App | 现代AP2优先原型候选；Android、密钥、依赖与实机仍待验证，见19 |
| [CastBay](https://github.com/weenas/castbay) | 较新UxPlay Android实现，独立airplay库，GPLv3，minSdk23 | 新增Android模块参考，与android-airplay-server比较；不继承整包/工具链，见19 |
| [android-airplay-server](https://github.com/jqssun/android-airplay-server) | 基于UxPlay的Android C/JNI、原生媒体、NSD与服务；GPLv3，minSdk24 | 保留Android主要参考，与CastBay按模块取舍，核查生命周期/低版本/子模块；见18/19 |
| [shairplay-rust](https://github.com/metaneutrons/shairplay-rust) | 现代AP2音频/配对，视频仍用legacy能力配置，AP2混合视频待研究 | 协议/音频参考，不作为现代AP2镜像已完成的证据；见19 |
| [PhairPlay](https://github.com/mazer666/PhairPlay) | Kotlin协议/媒体及原生PlayFair/ALAC，beta真机验证进行中；顶层Apache-2.0不覆盖全部组件判断 | 补充握手/同步/测试参考；已检查配对代码为raw-binary non-HomeKit路径，不以README“完整AirPlay 2”作为已验收结论；见18 |
| Jellyfin TV / Media3 | 原生电视播放器、API/依赖版本分界 | Standard采用Media3；Legacy用系统播放器，避免冻结旧依赖 |
| FFmpeg | 成熟TS封装/时间戳交织 | 仅最小封装子集，不带全量codec或命令行工具 |

该项目证明DLNA可以通过播放实时生成的视频显示桌面/PPT。此前“DLNA不能镜像桌面”的绝对说法不成立。限制在连续流/容器/codec兼容、电视预缓冲与实际性能，不在于画面来源是不是桌面。

其GOP选项或缓存上限不等于实测画面延迟。验证记录主要包括捕获、封装、MockRenderer等内容，并保留实际有声同步/硬件/外部渲染器的待验证项；不能由此承诺全部电视兼容。

## 4. 为什么全新方案不沿用通用运行时

GStreamer、Qt、.NET等本身有成熟生态，并非一定慢。这里不采用它们作为首版核心运行时，是因为目标功能范围已收敛，用户明确要求性能与包体优先、无需兼容旧代码。相应代价是原生媒体/界面适配和构建维护更复杂，必须用M1样机验证检验该决策。

不从零自写WebRTC、codec或TS封装算法。采用可裁剪的成熟核心库，平台硬编硬解与业务模块分离；这与继承整个通用框架或自研全部媒体栈是不同的工程取舍。
