# 22 HTTP生命周期与直播分发

更新：2026-11-07；D18合同延续至D26（0.6.11 / 19）。当前验证和源码范围见[08](08-实施进度与审阅入口.md)。本文件负责共享HTTP服务与DLNA直播订阅的所有权和分发合同；AirPlay媒体队列仍见[21](21-AirPlay媒体队列与资源生命周期.md)。

## 修复依据

原HTTP服务只保留监听任务，连接使用独立`tokio::spawn`。取消监听后的返回没有等待连接释放；直接中止监听任务还会留下连接。每连接的取消令牌在正常完成后也不会自动取消，相关请求工作可能继续存活。两项新增回环回归已在旧实现复现失败。

现在监听服务通过`JoinSet`拥有连接任务，同时最多四个；优先回收已完成任务后再接受新连接。撤销和监听错误均中止并等待连接任务回收；宿主直接丢弃/中止监听任务时，任务集也会中止其子任务。每连接通过取消守卫在正常返回、错误或被中止时通知关联工作。

0.6.8补齐传输背压：客户端发出请求后完全停止读取，原实现会永久等待写入，即使连接数有上限也会耗尽四个名额。新增虚拟时钟回归在原实现复现连接无法退出。现在`write_timeout`在首次写入/flush/shutdown返回Pending时启动15秒截止；正常进展重新开放下一次等待预算，到期先报TimedOut，再由HTTP任务释放请求和名额。TLS握手仍单独限制5秒，写入预算包裹握手后的TLS流。

适配器只保留一个可复用计时器，不复制媒体块、不增加后台任务，并保留vectored write。它没有整段视频时长限制；生产者空闲、起播和上游读取仍由各自模块管理。长时间暂停读取的播放器会断连，恢复播放需要重新发起Range/GET；真实电视的暂停/恢复行为仍需实机验证。

## 模块与所有权

| 模块 | 职责 | 边界 |
|---|---|---|
| [http_server](../crates/cast-adapters/src/http_server.rs) | IP过滤、最多四连接、TLS握手、HTTP解析、任务所有权和连接取消 | 不解释文件范围、直播门控或上游身份策略；不依赖Runtime/UI |
| [write_timeout](../crates/cast-adapters/src/write_timeout.rs) | 传输写入、flush及shutdown的连续阻塞截止 | 私有I/O适配器；不解释HTTP，不计入媒体数据等待时间 |
| [live](../crates/cast-adapters/src/live.rs) | 资源撤销、TS入口、私有订阅、容量/时间限制和分发 | `Subscription`拥有接收通道、起播门控和取消；仅编码后的TS进入此模块 |
| [live_session](../crates/cast-adapters/src/live_session.rs) | DLNA起播、状态监控、一次恢复及有界停止 | 私有monitor独立等待拉流进展、状态查询和Probe截止；不新增后台任务，不依赖UI |
| [ts](../crates/cast-adapters/src/ts.rs) | TS校验、PAT/PMT及实际SPS/PPS/IDR起播解析 | 不拥有网络任务或平台采集资源 |
| [media_http](../crates/cast-adapters/src/media_http.rs) / [legacy_bridge](../crates/cast-adapters/src/legacy_bridge.rs) | 文件Range/HEAD与固定HTTPS上游桥 | 共用连接生命周期，各自保留授权和响应策略 |

不新增crate或运行依赖。后续增加HTTP资源时，复用服务的任务所有权与请求取消令牌，资源自身处理授权、数据策略和撤销；不能在平台UI重新实现网络停止流程。正常`serve`返回是连接任务回收屏障；外部强制中止只发出子任务中止，调用方若需要确定完成应走资源撤销并等待监听退出。D22由Runtime独立持有资源任务，撤销后等待回收才交付stopped，文件顺序读取与取消位置提示合同见[26](26-截止与资源退出维护.md)。

## 分发与预算

TS入口仍验证每个数据块和65424字节上限；有活跃订阅者才创建一次`Bytes`分发分配。所有订阅者各自等待合法起点，门控通过后释放其解析状态，直接使用共享数据，不再经过`data.to_vec()`和重复逐包校验。跨FFI的输入寿命没有改变，入口需要的复制仍保留。

0.6.9将视频PES重组、连续计数和SPS/PPS/IDR检测封装为私有`VideoStart`；`StartGate`负责节目表和输出起点。遇到新的有效PAT时同时重置视频状态，未观察到PES起始包的续包既不解析也不进入起播输出。起播期间视频有效载荷必须连续，丢包或重复包返回`VIDEO_CONTINUITY_LOST`；计数15→0正常回绕，仅有adaptation的包不推进计数。已起播后的稳态TS仍由入口校验帧结构，门控不是完整通用MPEG-TS解码器。

NAL起始码改用一个32位滚动前缀，跨包保留状态；取消逐视频包的临时尾部向量扩展与搬移。入口一旦就绪即丢弃自己的门控对象，释放残留PAT/PES解析内存；订阅者仍分别寻找自己的可解码起点。没有新增运行依赖或旧协议回退。

| 约束 | 实现与行为 |
|---|---|
| 单订阅排队 | 16块，最多1,046,784字节；满队列关闭该订阅，不阻塞生产者 |
| 起播总时限 | 8秒；在读取队列前检查，已到期的订阅不能靠排队数据继续起播 |
| 不可解码起播窗口 | 最多2秒后重置解析，另保留解析器8MiB上限 |
| 已排队数据 | 超过2秒拒绝，避免持续补播过时画面 |
| 稳定播放等新数据 | 最多2秒，停止可立即打断等待 |
| 订阅关闭 | 丢弃响应/订阅即取消关联连接；撤销后拒绝保留迟到订阅 |

队列预算不等于进程内存预算，起播重组、当前块、Hyper/TLS/内核缓冲另外存在。共享分配测试证明两个稳定订阅者持有相同数据地址，没有实测CPU/RSS或端到端延迟提升百分比。

## D26 直播监控

此前监控在同一个循环中等待电视状态查询，单次查询含重试可能占用10秒，期间无法检查拉流或45秒Probe期限；用经过秒数取模选择查询时机还会受慢响应和调度延迟影响。现在三个future由会话直接持有并并发等待，拉流检查每秒执行，状态查询完成后间隔3秒再查，始终最多一个查询在途。连续三轮查询失败终止，查询成功清零失败次数；观察到拉流后电视报告STOPPED或NO_MEDIA_PRESENT则终止。

初次拉流和每次进展后的等待预算为10秒，先判断截止，再接受新的计数，迟到数据不能恢复过期阶段。Probe从Play确认后的监控开始计时，45秒截止独立于查询及数据；停止、超时或拉流中断会丢弃在途查询future。正常直播最多恢复一次，恢复前仍核对URI和PLAYING，重建期间记录新的字节进展，恢复成功重新发出pulling，避免界面永久停留在recovering。既有两秒有界、先核对URI的停止清理继续有效。

起播使用资源内的Notify通知，先注册再检查ready，避免丢失通知；不再每50毫秒唤醒。8秒起播截止和撤销优先，截止后的ready不能放行。该优化消除了等待期每秒约20次定时检查，没有改变媒体编码、网络协议或引入旧应用版本兼容。

## 验证与进度

七项新增Rust回归验证：正常结束取消及12次连接复用；四连接上限和释放后重连；正常停止/强制中止释放请求所有权；两个稳定订阅共享分配；积压数据不能延长起播截止；过时数据与等待撤销；丢弃及迟到订阅不留活跃读者。原有慢读者隔离、文件Range/HEAD/撤销和Legacy固定身份回环继续运行。

0.6.8增加停读响应释放连接、长期有进展的传输、生产者空闲不误超时、截止后的迟到可写及vectored write回归；全部使用虚拟时钟和受控双工缓冲，无墙钟毫秒阈值依赖。

0.6.9新增四项起播回归：缺失PES起点、PAT替换未完成PES、视频丢包，以及PES/NAL所有分片点与连续计数回绕/adaptation包。前三项先在原实现复现失败，再验证修复；实际合成TS仍通过现有中途加入、重分片及HTTP回环，FFmpeg解码由Linux原生媒体CI验证。

0.6.11新增八项虚拟时钟回归：慢查询不阻塞拉流截止、持续媒体下Probe仍到期、查询节奏及失败计数复位、恢复必须观察新数据并报告pulling、迟到数据拒绝、电视停止及取消释放查询、就绪通知与撤销、缺失及迟到起播。现有validate_live改为会话先于媒体入口启动，使用真实TS验证通知到HTTP/SOAP的完整路径。
