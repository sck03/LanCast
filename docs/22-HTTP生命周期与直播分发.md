# 22 HTTP生命周期与直播分发

更新：2026-11-10；D18合同延续至D44（0.6.29 / 37）。当前验证和源码范围见[08](08-实施进度与审阅入口.md)。本文件负责HTTP客户端、共享HTTP服务与DLNA直播订阅的所有权和分发合同；AirPlay媒体队列仍见[21](21-AirPlay媒体队列与资源生命周期.md)。

## 修复依据

原HTTP服务只保留监听任务，连接使用独立`tokio::spawn`。取消监听后的返回没有等待连接释放；直接中止监听任务还会留下连接。每连接的取消令牌在正常完成后也不会自动取消，相关请求工作可能继续存活。两项新增回环回归已在旧实现复现失败。

现在监听服务通过`JoinSet`拥有连接任务，同时最多四个；优先回收已完成任务后再接受新连接。撤销和监听错误均中止并等待连接任务回收；宿主直接丢弃/中止监听任务时，任务集也会中止其子任务。每连接通过取消守卫在正常返回、错误或被中止时通知关联工作。

0.6.8补齐传输背压：客户端发出请求后完全停止读取，原实现会永久等待写入，即使连接数有上限也会耗尽四个名额。新增虚拟时钟回归在原实现复现连接无法退出。现在`write_timeout`在首次写入/flush/shutdown返回Pending时启动15秒截止；正常进展重新开放下一次等待预算，到期先报TimedOut，再由HTTP任务释放请求和名额。TLS握手仍单独限制5秒，写入预算包裹握手后的TLS流。

适配器最多保留一个可复用计时器，首次阻塞才分配；写入、flush及shutdown分别记录截止，同一操作完成才清除自己的截止。它不复制媒体块、不增加后台任务，并保留vectored write。没有整段视频时长限制；生产者空闲、起播和上游读取仍由各自模块管理。长时间暂停读取的播放器会断连，恢复播放需要重新发起Range/GET；真实电视的暂停/恢复行为仍需实机验证。

## D44 HTTP客户端与信任边界

DLNA和媒体桥共用`http_client`：禁用代理、自动重定向与库内自动重试，使用HTTP/1，每个主机最多保留一个空闲连接。此前默认空闲池没有每主机数量上限；并发请求结束后，多余套接字可保留至默认空闲期限。真实TCP回归同时建立三条连接，要求结束后及时关闭两条、保留一条供复用；恢复原无限上限时该回归失败。并发请求仍可正常建立连接，空闲上限不是在途请求上限。

连接与读取截止均为5秒；DLNA另保留完整请求含body的5秒总期限和512KiB XML上限。媒体桥没有整段视频总时限，响应头阶段最多5秒，body按读取进展重置空闲期限。真实TLS回环验证持续缓慢发头仍返回502，连续6秒媒体交付正常。慢响应头保护在旧版本也通过，本轮没有把它列作新增修复或叠加重复计时器。

保留Hyper默认的100个响应头上限及栈上解析缓冲，101个头拒绝；不使用会为每个响应增加堆分配的自定义数量设置。公开证书路径拒绝自签名媒体身份，媒体桥仅接受配对指纹；已有Range、HEAD、错误指纹和撤销回归继续执行。重试由业务层负责：只读SOAP查询最多再执行一次，播放、停止、跳转等动作不自动重试。

新模块集中连接政策，`auth`继续拥有配对指纹验证，`dlna`保留SOAP/总期限，`legacy_bridge`保留媒体流和资源撤销。没有新增后台任务、周期轮询或旧应用协议回退。上游计时器复用与空闲池预算是可核对的资源路径变化；本轮未测量真实投屏CPU、RSS、延迟或长稳性能。

## 分发与预算

TS入口仍验证每个数据块和65424字节上限；有活跃订阅者才创建一次`Bytes`分发分配。所有订阅者各自等待合法起点，门控通过后释放其解析状态，直接使用共享数据，不再经过`data.to_vec()`和重复逐包校验。跨FFI的输入寿命没有改变，入口需要的复制仍保留。

0.6.9将视频PES重组、连续计数和SPS/PPS/IDR检测封装为私有`VideoStart`；`StartGate`负责节目表和输出起点。内容变化的有效PAT同时重置视频状态，完全相同的PAT重传保留正在重组的视频（D39）；未观察到PES起始包的续包既不解析也不进入起播输出。起播期间视频有效载荷必须连续，丢包或重复包返回`VIDEO_CONTINUITY_LOST`；计数15→0正常回绕，仅有adaptation的包不推进计数。已起播后的稳态TS仍由入口校验帧结构，门控不是完整通用MPEG-TS解码器。

NAL起始码改用一个32位滚动前缀，跨包保留状态；取消逐视频包的临时尾部向量扩展与搬移。入口一旦就绪即丢弃自己的门控对象，释放残留PAT/PES解析内存；订阅者仍分别寻找自己的可解码起点。没有新增运行依赖或旧协议回退。

| 约束 | 实现与行为 |
|---|---|
| 单订阅排队 | 16块，最多1,046,784字节；满队列关闭该订阅，不阻塞生产者 |
| 起播总时限 | 8秒；在读取队列前检查，已到期的订阅不能靠排队数据继续起播 |
| 不可解码起播窗口 | 最多2秒后重置解析，另保留解析器8MiB上限 |
| 已排队数据 | 超过2秒拒绝，避免持续补播过时画面 |
| 稳定播放等新数据 | 最多2秒，停止可立即打断等待 |
| 订阅关闭 | 丢弃响应/订阅即取消关联连接；撤销后拒绝保留迟到订阅 |

队列预算不等于进程内存预算，起播重组、当前块、Hyper/TLS/内核缓冲另外存在。共享分配测试证明两个稳定订阅者持有相同数据地址，没有实测CPU/RSS或端到端延迟提升百分比。

## D26 直播监控

此前监控在同一个循环中等待电视状态查询，单次查询含重试可能占用10秒，期间无法检查拉流或45秒Probe期限；用经过秒数取模选择查询时机还会受慢响应和调度延迟影响。现在三个future由会话直接持有并并发等待，拉流检查每秒执行，状态查询完成后间隔3秒再查，始终最多一个查询在途。连续三轮查询失败终止，查询成功清零失败次数；观察到拉流后电视报告STOPPED或NO_MEDIA_PRESENT则终止。

初次拉流和每次进展后的等待预算为10秒，先判断截止，再接受新的计数，迟到数据不能恢复过期阶段。Probe从Play确认后的监控开始计时，45秒截止独立于查询及数据；停止、超时或拉流中断会丢弃在途查询future。正常直播最多恢复一次，恢复前仍核对URI和PLAYING，重建期间记录新的字节进展，恢复成功重新发出pulling，避免界面永久停留在recovering。既有两秒有界、先核对URI的停止清理继续有效。

起播使用资源内的Notify通知，先注册再检查ready，避免丢失通知；不再每50毫秒唤醒。8秒起播截止和撤销优先，截止后的ready不能放行。该优化消除了等待期每秒约20次定时检查，没有改变媒体编码、网络协议或引入旧应用版本兼容。

## D27 节目表切换与解析分配

起播阶段，PMT内容发生变化（含版本、视频PID或编码类型）时，必须重新等待新流的完整PES及SPS/PPS/IDR。旧实现只覆盖视频PID，保留连续计数和参数集状态；新PMT没有H.264时甚至保留旧PID。两项新增回归在原实现复现错误放行。现在`StartGate`原子更新视频选择、清除`VideoStart`，输出缓存缩至最近一次已通过CRC的PAT，再加入新PMT的全部TS分片。损坏或未完成的后续PAT不能替换已确认的起播前缀；完全相同的重复PMT不会打断正在重组的关键帧。

私有`video_pid`负责PMT结构和描述长度校验，越过CRC边界的节目/流描述直接报错；私有`pes_offset`负责PES头界限。节目表、视频起播和网络生命周期继续各自持有状态，没有引入平台依赖或旧协议回退。

`SectionAssembler`返回借用的完成节并复用缓冲，避免每次完成PAT/PMT都转移并重新分配向量。完整PES头在原输入上计算偏移并扫描视频，仅跨TS包的头使用临时重组；PES可选头中的类似NAL起始码不会当成视频数据。这是解析分配的减少，不能据此推算进程RSS或端到端帧率提升。

## D34 交错写入与关闭截止

原适配器用一个waiting标记记录所有输出操作，任何操作成功都会清除标记。HTTP引擎每次poll_shutdown前都会先flush；若shutdown仍阻塞，但flush成功，其他唤醒反复进入这一流程就会延长关闭期限。flush插入尚未完成的写入也有同样问题。两项虚拟时钟回归先在旧实现复现失败。

现在三个操作各有固定截止，共用最早截止的一个计时器；vectored和普通写入共用写入截止。每次先检查所有在途截止，再调用底层流，迟到的就绪不能恢复已超时连接。HTTP集成回归通过真实Hyper连接和受控停滞关闭验证：连续重新轮询仍在15秒释放连接并取消请求工作。原有写入进展续期、闲置生产者和慢读者回归继续适用。

计时器首次Pending才分配，并在连接内复用。`auth`统一产生含32字节随机数的URL-safe无填充媒体令牌；媒体文件、直播和固定上游桥删除两次字符串replace，文件和直播资源在创建时保存完整路径，后续请求直接进行常量时间比较。配对挑战仍使用原有标准Base64编码；媒体URL是会话内临时资源，不提供旧URL恢复或迁移层。现有TLS指纹、Range、HEAD、撤销和直播回环负责验证调用边界。

这些改动减少连接/请求路径的分配并保证阻塞退出期限，没有新增运行依赖、线程或队列；未据此宣称CPU、RSS或端到端延迟的实测改善。

## D35 起播边界与节目身份

原门控处理完整个写入块后才发布起播点。如果首个有效IDR后同批出现新PAT，它会遗漏该PAT；后续PMT还可能重置已成立的起播点。因此同一TS按单包或批量写入会得到不同输出。现在在首次检测到有效SPS/PPS/IDR的TS包后立即结束起播解析，拼接本次写入剩余数据并原样传递后续块。入口仍先校验整个块的TS结构，65424字节输入和8MiB起播输出上限继续生效。门控完成即释放节目表和PES临时缓冲；批量写入的剩余部分不再执行起播解析或CRC计算。

起播前，私有`Program`同时保存PAT选中的节目编号与PMT PID。空PAT或只含网络信息的PAT会清除旧节目及视频状态，迟到的旧视频不能放行；PMT仅在节目编号匹配时才生效。`pat_program`集中校验PAT固定头、CRC尾部和完整四字节条目，拒绝截断条目；不接受残缺节目映射。既有CRC失败不替换有效表、重复PMT不中断关键帧、视频连续计数等合同继续有效。

三项回归先在旧实现失败：起播后的节目切换随分块方式改变输出、移除节目后仍使用旧视频、同PID上接受其他节目的PMT。另补畸形PAT和起播点之后仍校验TS结构的回归。真实合成TS验证器对三个加入位置分别使用1、7、348包/次写入，要求输出逐字节相同，并保留四种PES/PSI重分片与HTTP回环；Linux原生媒体工作流对生成结果实际解码。

调整局限于TS解析模块及验证器；平台层、网络任务与媒体采集无需新增分支，没有新增运行依赖或旧应用协议回退。减少解析工作和临时状态滞留不等于已有CPU/RSS或端到端延迟的实机测量。

## D39 重复PAT与起播连续性

原门控在每次收到有效PAT时清空PMT、视频PES和起播缓存。关键帧跨包传输时，即使PAT内容完全相同，周期重传也会丢弃已收到的视频起点。新增回归先在原实现复现空输出；现在仅完整、CRC有效且内容变化的PAT更新节目并重置解析状态。表内容比较包含节目、版本和CRC，不受TS连续计数或分片位置影响；真正的节目切换仍清除旧视频状态。

已选中节目时，重复PAT的全部TS包按输入顺序进入起播缓存，视频PES头和NAL前缀继续重组。尚未取得SPS参数集时，新的PES起点将缓存缩至已确认的PAT/PMT前缀，排除关键帧前无法解码的普通帧；参数集已就绪时保留跨PES数据。私有`append`统一检查普通包、PAT包及起播后同批尾部的8MiB缓存上限，删除重复检查，单独重传PAT不能重置预算。新增5项回归覆盖所有PAT分片点及1/2/7包写入、未完成PES头、重传累计上限、不可解码前缀排除及跨PES参数集保留；原有PAT变更回归改用实际版本变化。

Linux原生媒体CI对每份输出分别执行FFmpeg，并同时要求退出成功和error级日志为空。FFmpeg在探测阶段可能报告缺失PPS却退出0，仅凭退出码会遗漏错误；实际运行发现该问题后，已补充前缀回归和严格检查，最终解码证据见08。

变化局限于TS模块，网络及平台接口无需修改。额外保存一份最多1024字节有效内容的PAT比较缓冲，在表更新时复用，起播就绪后随门控状态释放；不新增依赖、线程、轮询或旧应用兼容分支。避免无效重置有助于保留首个可解码关键帧，但尚无实机CPU/RSS或端到端延迟测量。
