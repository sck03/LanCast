# 05 构建依赖与包体控制

本文件记录原始包体和发行目标。Windows RTC已按D08改为固定源码libdatachannel/Mbed TLS/libopus；Android仍使用固定上游AAR，定制源构建与裁剪未完成。Cargo.lock、Gradle wrapper、FFmpeg源哈希和Actions已落实；脚本存在不等于构建成功。

## 1. 工具链

| 部分 | 基线 |
|---|---|
| Rust | 1.98.1，edition2024；Windows MSVC目标、Android ARM32/ARM64目标 |
| Android | JDK17，Kotlin2.3.10，AGP8.13.2，Gradle8.13 |
| Android SDK | compile/target36；Build Tools35.0.0 |
| Android native包装/TS | NDK27.2.12479018，CMake3.22.1 |
| Windows应用/外围C ABI | VS2022 v143/14.44，Windows SDK10.0.26100.0，CMake3.31.6，C++20 |
| Windows RTC与C++桥 | 固定libdatachannel/Mbed TLS/libopus源码，MSVC静态CRT；C ABI 2 |
| Android定制libwebrtc目标 | 固定源revision的GN/Ninja/DEPS工具链；当前使用明确固定的上游AAR，源构建未完成 |
| Android Standard播放器 | Media3 1.11.1，所有Media3模块同版本 |
| Android Legacy播放器 | 系统MediaPlayer，不引入旧Media3 |

| Apple | Rust1.98.1 Apple targets、Xcode、XcodeGen2.44.1、LiveKitWebRTC150.7871.02；SDK实际版本随报告归档，见D09 |

Android定制libwebrtc的历史源基线是webrtc-sdk/webrtc提交0385653a83f21acf3c916466d4088b29fe2f160b；它是开源fork，不假称Google官方Maven产物。当前正式输入仍是固定上游AAR，不能把源基线当成已构建产物。Windows改用D08的源构建RTC组件，准确提交、补丁、配置和产物哈希随材料保存。

不根据文件夹里“碰巧存在libwebrtc.aar”自动覆盖依赖。Android默认固定上游版本，自建输入只能显式指定；不同平台和ABI不混用二进制。不要照搬指向旧版本或浮动main的历史脚本。

## 2. 免费开源组件选择

| 能力 | 选择 | 许可/控制点 |
|---|---|---|
| 实时媒体 | Android libwebrtc；Windows libdatachannel/libopus/Mbed TLS | BSD/MPL-2.0/Apache-2.0及附带第三方许可；实际输入见D08 |
| TS封装 | FFmpeg avformat/avcodec/avutil必要子集 | 基础LGPL；禁用GPL/nonfree及无关依赖，检查真实构建配置 |
| Android播放器 | Media3 | Apache-2.0；仅Standard接收端 |
| 异步运行时 | Tokio 1.x | MIT；仅启用网络/时间/同步等所需feature |
| HTTP/WebSocket | Hyper 1.x、tokio-tungstenite | MIT系；使用成熟解析器，不手写HTTP解析 |
| TLS | rustls 0.23系、tokio-rustls | Apache/MIT/ISC等；固定一种crypto provider，避免重复实现 |
| 序列化/URL/XML | serde/serde_json、url、quick-xml | 开源许可；拒绝重复键、DTD/外部实体、无限解析 |
| 发现 | mdns-sd及受限SSDP适配 | 开源库；SSDP控制逻辑在独立模块 |
| 身份/随机 | rcgen、p256、sha2、系统安全随机源 | 使用成熟实现，不自写密码算法 |

Rust依赖的精确patch版本与传递feature在首个工程提交的Cargo.lock/构建清单一次性固定；本文固定API主线，不杜撰尚未解析的完整依赖树。发布构建禁止latest、浮动Git分支与自动更新。升级由独立任务更新锁文件、SBOM和兼容测试，不能在用户运行时下载新库。

当前`dependency-report.py`从锁定的Cargo解析图生成Rust源码SPDX 2.3及条件依赖报告，由Linux/Windows Actions归档；采集与纯转换模块分离。复查命令、字段语义及完整二进制SBOM的剩余范围见[15 依赖审阅契约](15-Rust依赖清单与审阅契约.md)。

不采购收费投屏SDK；不将Sunshine/Moonlight/UxPlay的GPL实现直接复制到主体。免费/开源不等于codec专利、Apple/Google生态与商店分发条件完全豁免，发布时按实际地区与分发方式核查。

[D15](18-AirPlay按需接收设计与接入方案.md)在0.6.0锁定rairplay及PlayFair源码快照，以独立GPL工作区与Android Airplay产品变体集成。`airplay-native/Cargo.lock`独立固定传递依赖；未使用GStreamer、额外FFmpeg解码器或付费SDK。原Standard/Legacy和发送APK不链接AirPlay模块；包含模块的组合APK按GPL-3.0-only分发，运行开关关闭不消除许可义务。原始Git文件哈希、修改后源码、依赖清单及Cargo源码包随构建归档。详见[20实现与分发](20-AirPlay实现与审阅指南.md)与THIRD_PARTY；正式发行审计仍是独立门槛。

Android模块/协议对照仍保留CastBay、android-airplay-server和PhairPlay调研；本轮宿主、JNI和播放器按LanCast合同实现，不复制整套应用。使用系统MediaCodec/AudioTrack，AAC-LC与AAC-ELD单独处理，ALAC/HEVC/HLS/PTP/type103不公告为可用。固定开发身份已替换为私有存储中的随机身份，可信公钥原子落盘，每次媒体接入仍需电视确认。密码依赖的准确版本以独立锁文件和CI清单为准，SRP预发布依赖的后续升级需重跑完整配对回环测试。

## 3. 裁剪原则

libwebrtc：release构建，关闭示例/测试程序、未用服务和未注册codec，保留H.264/Opus、DTLS/SRTP、拥塞/同步所需能力。裁剪开关必须是固定源码真实存在的GN参数，并验证互通；不能仅在UI隐藏codec就宣称二进制已移除。

FFmpeg：从disable-everything启用mpegts muxer、h264_metadata BSF及必要内部依赖；无命令行程序、设备输入、网络、通用编码器/解码器、像素滤镜集合、GPL/nonfree。H.264/AAC由平台编码，FFmpeg封装并修正Windows硬编可能遗漏的SPS/VUI色彩标记；不重新编码图像。记录真实configure、链接和许可结果。

Windows TS的Release/MinSizeRel链接额外使用GNU链接器已有的`-s`，去除静态FFmpeg/GCC输入携带的DWARF调试段和COFF符号表。保留导出表、导入表、重定位、异常展开信息；Debug/RelWithDebInfo仍保留调试信息。裁剪后再执行TS契约测试，发行检查拒绝Release DLL重新夹带调试段；无需增加压缩壳或新运行库。源码/重链接材料与许可证继续独立归档，测量结果见08。

Rust：feature按角色启用；接收端不编入DLNA发送、录屏编码、TS mux。release使用LTO/符号分离，保留独立调试符号用于崩溃定位。不要为了少几百KB引入不安全自写解析器或删除故障诊断。

UI：使用原生控件；不带浏览器、Qt/.NET或GStreamer完整运行时。资源压缩、字体/图片去重，避免内置大视频测试文件；测试片放在开发测试包，正式包运行时生成小型合成探针。

D13桌面改造复用Windows系统绘图/网络/托盘API，ICO从既有LanCast标识生成并直接嵌入EXE。Python/Pillow只用于开发时重新生成图标，不是构建或运行依赖；新增桌面契约测试不进入用户包。清理构建缓存释放的磁盘空间与产品下载体积分别报告，见[16](16-Windows易用性与桌面模块.md)。

## 4. 按角色与ABI打包

| 包 | RTC | TS/AAC发送 | 文件播放器 | Legacy媒体桥 |
|---|---|---|---|---|
| Receiver Standard | 接收 | 不包含 | Media3 | 不包含 |
| Receiver Legacy | 接收 | 不包含 | 系统播放器 | 包含 |
| Sender Android | 发送 | 包含 | 不包含 | 不包含 |
| Windows Sender | 发送 | 包含 | 不带电视播放器 | 不包含 |
| Apple Mac/iOS | 发送与接收 | 不包含 | AVPlayer | 包含；用于固定SPKI HTTPS上游 |
| Apple tvOS | 接收 | 不包含 | AVPlayer | 包含；Rust关闭sender feature |

Android两个接收产品变体各提供ARMv7a和ARM64定向包，手机发送也按ABI交付；产品版本与CPU包不是同一个概念。支持的商店可用AAB按设备拆分，侧载渠道提供明确ABI标识的APK；不默认把全部ABI塞进低存储电视。开发用universal包不作为正式包体指标。

这些是首版发布物设计，不能把不同系统版本强行打进同一依赖图。所有共享代码通过端口复用，而非给Legacy打包一套用不到的新播放器。

D15另设构建期AirPlay模块裁剪与运行期开关：不含模块的构建不带相关库/服务声明、不提供可用开关；含模块的构建仍默认关闭。运行时关闭只表示未启动服务，不能宣称已减小安装包。选型后单独记录每个ABI的包体和待机/播放资源增量；现有发送端及Apple包不因D15引入AirPlay依赖。

## 5. 包体和资源预算

以下为优化与评审目标，尚无构建实测：Standard单ABI APK≤30MiB，Legacy≤24MiB，Sender≤35MiB；Windows x64压缩分发包≤65MiB。超额必须提交组成报告和优化结果，不能伪造数据或删掉必要安全功能以通过门槛。

CI对产物按模块/库/ABI报告大小，较基线增长超过5%触发评审；重复codec、重复TLS provider、整包SDK、调试符号误入包体列为检查项。将源代码体积、下载大小、安装后占用、运行时RSS分别记录。

启动后无会话时不初始化编码器，不持续采屏或轮询解码器；按需加载媒体模块，结束释放。性能预算以真实设备为准，不能以语言名称推断流畅度。

## 6. 后续构建流程

1. 建立全新仓库结构与工具chain文件，锁定源tar/Git revision及下载SHA256。
2. Windows构建D08的RTC库与C ABI桥；Android解析固定AAR或显式自建输入，各自记录ABI、配置和哈希。
3. 构建最小FFmpeg和TS桥，仅链接到发送目标；验证没有多余codec/网络/程序。
4. 构建Rust domain/core/adapters/ffi，针对角色feature产生动态/静态库，检查接口版本。
5. 构建Android三角色/ABI和Windows客户端，检查合并manifest、依赖图、native加载与16KB页要求。
6. 运行契约/集成测试，再做真机和包体分析。release签名、更新回退、许可证/源码获取说明作为发布步骤。

实际脚本见scripts与.github/workflows；各作业独立报告成功/失败，不能用Rust成功代替Android/Windows/媒体库成功。
