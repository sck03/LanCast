# 09 原生媒体实现与构建决策

2026-10-03，D08。本决策取代 D07 中 Windows 必须自建完整 libwebrtc 的依赖选择。06 的实机验收门槛不变。

## 技术选择

Windows 使用 WGC、D3D11 Video Processor、Media Foundation 硬件 H.264、WASAPI loopback。RTC 采用固定源码 libdatachannel 0.23.2、libopus 1.5.2 和 Mbed TLS 3.6.4，通过 ICE、DTLS/SRTP、RTP/RTCP 与 Android libwebrtc 互通，不附带另一套通用视频编解码器。实际跨实现互通需单独验收。

libdatachannel 为 MPL-2.0；libopus 为 BSD；Mbed TLS 选择 Apache-2.0。准确提交位于 windows/media/CMakeLists.txt、scripts/build-windows-deps.ps1，传递源码使用固定子模块。RTC 库和自有桥在同一 MSVC 工具链编译，向 Win32 暴露 C ABI 2。

Android 使用固定 webrtc-sdk AAR 150.7871.01、硬件 factory 与 H.264 协商。这是明确的上游二进制输入，不宣称已经实现定制源构建或二进制 codec 裁剪。原方案的自建库发行仍需独立供应链工作。自建 AAR 只能用显式 lancastWebrtcAar 参数，不会隐式替换。

## 模块和数据路径

| 模块 | 输入 → 输出 | 边界 |
|---|---|---|
| capture | WGC纹理或合成帧 → GPU NV12 | 不发现电视、不读配对凭据 |
| encoder | NV12 → H.264；PCM → AAC | 不操作UI、不请求权限 |
| h264_metadata | 硬编H.264 → SPS/VUI标记齐全的H.264 | FFmpeg BSF复制编码slice，不解码、不重新编码 |
| audio | WASAPI系统输出 → PCM | 不启用麦克风 |
| rtc_channel | H.264/Opus → RTP/DTLS/SRTP | 不接触原始像素 |
| ts_output | H.264/AAC → 最小TS DLL | 不发HTTP或SOAP |
| backend | 句柄、实例、回调和异常边界 | 不维护设备档案 |
| Rust live_session | TS就绪、UPnP起播、拉流、取消/恢复 | 不启动屏幕捕获 |
| Android ProbeFrames | EGL合成颜色 → 编码器Surface | 不用录屏、录音或播放采集权限 |

像素不穿过 Rust/JNI。每实例专用线程处理采集、编码与输出；异步 MFT 事件由同线程消费。Windows 当前最大720p30，按协商降低。窗口图像可能配全系统声音，UI明示。无硬编/D3D11输入/媒体组件时明确失败，不切换GDI/JPEG；尺寸或声音设备变化要求重启分享。HDR与跨显卡须验收后扩大声明。

## DLNA 流程

1. 用户选择电视、声音配置并测试。生成彩色画面及提示音，不采集用户内容。
2. 创建限定目标IP/token的资源，等待PAT/PMT/SPS/PPS/IDR，再Load/Play。写超时先查询CurrentURI/播放状态，不盲重试。
3. 10秒内观察到合法TS向HTTP层输出。HEAD、GET次数或SOAP PLAYING不等于通过。
4. 用户在电视确认持续画面和所选声音；45秒未确认则停止。确认后保存证据并结束测试。
5. 再次点击分享才开始真实采集授权。签名、1280×720@30和声音配置必须匹配；30天到期或时钟回退失效。文件能力独立。
6. 停止拉流后最多一次重建；先确认电视仍播放本URL。电视停止/换源时不抢占。旧会话Stop完成后才能建立新直播。

档案在Android私有files、Windows %LOCALAPPDATA%/LanCast/receiver-profiles.json；schemaVersion=1，临时文件同步后原子替换，不保存授权/token/媒体。UPnP不提供固件字段时不能自动识别升级，用户须重测。

## 构建与证据

Actions运行Rust双系统、真实TS分片与HTTP/UPnP模拟电视、Windows媒体/RTC回环、Android APK/lint/ABI。RTP回环不等于解码，TS解码不等于电视显示。性能使用真实设备测量。

Windows最小TS DLL由UCRT64构建，控制与RTC由MSVC构建；跨界只使用C ABI借用字节，不传STL或跨库释放内存。脚本检查源SHA256并禁用FFmpeg GPL/nonfree及无关模块。

本机AMD MFT忽略MF媒体类型上的色彩属性，四项ICodecAPI色彩控制均返回E_NOTIMPL。因此不能把SetUINT32成功当成SPS已经写入BT.709；编码后使用固定FFmpeg的h264_metadata过滤器明确写入BT.709/有限范围，再分别交给RTC或TS。过滤器只修改元数据，由解码内容测试验证，异常保留真实输出端错误。
