# 13 独立平台构建与版本配置

每个系统有自己的 GitHub Actions 文件和构建入口，独立触发、取消、查看日志、重跑和上传产物。平台之间不使用同一个矩阵工作流；共享 Python 工具只处理一致的参数校验、依赖准备和报告。

五个平台的默认与自定义版本构建已实际通过，运行、版本元数据与下载校验见[08验证记录](08-实施进度与审阅入口.md)。不同手动参数使用不同取消分组，重复同一组才取消旧运行。

| 系统 | GitHub 工作流 | 本地产品构建入口 |
|---|---|---|
| Windows x64 | [windows.yml](https://github.com/sck03/LanCast/actions/workflows/windows.yml) | `python scripts/build-windows.py` |
| Android 三个产品 | [android.yml](https://github.com/sck03/LanCast/actions/workflows/android.yml) | `python scripts/build-android.py` |
| macOS 通用包 | [macos.yml](https://github.com/sck03/LanCast/actions/workflows/macos.yml) | `python3 scripts/build-macos.py` |

## 手动构建参数

在对应 Actions 页面选择 **Run workflow**。下面四个参数对五个平台一致：

| 参数 | 默认/限制 | 实际作用 |
|---|---|---|
| source_ref | 留空使用所选工作流 ref 对应 SHA；可填分支、标签或提交 | checkout 实际源码；报告记录解析后的 SHA |
| version | 留空取 build-config.json | 数字 major.minor.patch，各段0–9999；各端统一数值格式 |
| build_number | 留空取清单；1–65535 | APK versionCode、Apple CFBundleVersion、Windows文件版本第四段 |
| configuration | Windows/macOS 默认 Release，其余 Debug | 应用编译模式、构建任务、包目录和产物标识 |

输入先校验再导出环境，不把输入文本拼进 shell。选用的历史源码必须包含当前构建接口和版本清单；早期不支持这些参数的提交应使用它当时的工作流。source_ref 控制产品源码，GitHub 的工作流分支选择控制工作流定义。

版本号写入 Android versionName、Apple CFBundleShortVersionString 和 Windows ProductVersion，构建号写入对应包元数据。构建后检查实际 APK、Info.plist、PE 资源与参数一致。产物名包含版本、构建号、模式；`dist/reports/build-<platform>.json` 或 Apple `build-report.json` 保留源码 SHA、生效参数和校验结果，平台产物附 SHA-256。

应用默认版本以仓库根目录 `build-config.json` 为单一入口。Python 参数优先于 LC_VERSION/LC_BUILD_NUMBER/LC_CONFIGURATION 环境，其后才是清单；Android Gradle/CMake 本地构建也读取同一清单。Android 升级已有安装时应增加构建号，并使用相同签名。

```sh
python scripts/build-android.py --version 0.4.1 --build-number 41 --configuration Release
python scripts/build-windows.py --version 0.4.1 --build-number 41 --configuration Debug
python3 scripts/build-macos.py --version 0.4.1 --build-number 41 --configuration Release
python3 scripts/build-ios.py --version 0.4.1 --build-number 41 --configuration Release
python3 scripts/build-tvos.py --version 0.4.1 --build-number 41 --configuration Release
```

Android 本地需先按 README 准备 Rust/JNI，Windows 需先准备固定的 TS/DTLS 依赖和 VS2022；Actions 会自动完成这些前置步骤。Rust、FFmpeg 和固定依赖继续使用其已验证构建方式，configuration 控制产品的 Kotlin/Xcode/C++ 构建。Windows Debug 保留调试信息和关闭优化，但仍使用与固定 DTLS 库一致的静态 Release CRT。

Release 是优化构建模式。Android Release APK 和 iOS/tvOS 设备 App 未配置正式签名，Mac 交付包也不自动公证；本项目不会因为选择 Release 就发布商店或 GitHub Release。签名发行、SBOM、真机兼容与性能是独立退出门槛。

## 通过仓库脚本触发与查看

```sh
python scripts/github-ci.py --dispatch --workflow android.yml --ref main --source-ref main --version 0.4.1 --build-number 41 --configuration Release
python scripts/github-ci.py --workflow android.yml --artifacts
python scripts/github-ci.py --run <run-id> --failed-logs
python scripts/github-ci.py --run <run-id> --download <artifact-name>
```

脚本复用 Git 凭据，凭据不输出、不落盘。源码标签、版本号与构建参数进入 GitHub 的结构化请求。查看自定义 source_ref 运行时，以产物报告的 source_commit 为准：Actions 的 head_sha 指工作流所在提交，两者可能不同。

依赖版本不在手动构建页面任意覆盖。Rust Cargo.lock、Gradle/WebRTC 固定坐标、原生 CMake 固定提交、FFmpeg/Apple 下载版本与校验值继续随仓库审阅；改依赖时独立提交并执行受影响平台回归，见05与THIRD_PARTY。
