# 13 独立平台构建与版本配置

日期：2026-10-08；D16 构建整理。应用默认版本由根目录 `build-config.json` 管理，当前为 0.6.1 / 9 开发版。实际构建、回归与未完成验收统一记录在[08](08-实施进度与审阅入口.md)。

## 工作流与产品角色

五个平台各有独立工作流；另外三个工作流只做检查。文件名保持稳定，Actions 页面名称标注用途。平台之间独立触发、取消和上传，不需要先运行另一个平台。

| 工作流 | 产品角色或检查范围 | 产品入口 |
|---|---|---|
| [windows.yml](https://github.com/sck03/LanCast/actions/workflows/windows.yml) | Windows x64 **发送端** | `scripts/build-windows.py` |
| [android.yml](https://github.com/sck03/LanCast/actions/workflows/android.yml) | **1 个发送端 + 3 个接收端**，支持选择构建 | `scripts/build-android.py` |
| [macos.yml](https://github.com/sck03/LanCast/actions/workflows/macos.yml) | macOS 通用 App，发送与接收 | `scripts/build-macos.py` |
| [ios.yml](https://github.com/sck03/LanCast/actions/workflows/ios.yml) | iPhone/iPad 发送与前台接收；含 ReplayKit 扩展 | `scripts/build-ios.py` |
| [tvos.yml](https://github.com/sck03/LanCast/actions/workflows/tvos.yml) | Apple TV **接收端** | `scripts/build-tvos.py` |
| [core-linux.yml](https://github.com/sck03/LanCast/actions/workflows/core-linux.yml) | Rust 核心、架构、脚本测试、Actionlint 与依赖报告 | 不生成客户端 |
| [native-linux.yml](https://github.com/sck03/LanCast/actions/workflows/native-linux.yml) | TS/H.264/HTTP 合成媒体回归 | 不生成客户端 |
| [airplay.yml](https://github.com/sck03/LanCast/actions/workflows/airplay.yml) | 独立 AirPlay 协议工作区的 fmt、Clippy 和回环测试 | **不生成 APK**；APK 在 Android 工作流 |

推送 `main` 和 PR 按各自 `paths` 触发受影响的检查；只改文档通常不会重编译。共享核心改变会触发相关平台，AirPlay 改变会触发 Android/协议检查。Linux 核心检查覆盖所有 `scripts/**` 和工作流变更，防止新共享工具未触发回归。完整验收时可手动补跑所有八个工作流；某项未触发应标为“未运行”，不能视为通过。

## Android 四个 APK 怎么选

| 产品 / 下载名前缀 | 角色 | 最低系统 | 适用场景 / 应用 ID |
|---|---|---|---|
| `LanCast-Android-Sender-` | 发送端 | Android 10 / API29 | 从手机发送屏幕、声音或文件；`dev.lancast.sender` |
| `LanCast-Android-Receiver-Standard-` | 接收端 | Android 6 / API23 | 常规电视优先选择，自有投屏与 Media3 文件播放；`dev.lancast.receiver` |
| `LanCast-Android-Receiver-Legacy-` | 接收端 | Android 5 / API21 | 旧系统或需要系统播放器的设备；`dev.lancast.receiver.legacy` |
| `LanCast-Android-Receiver-AirPlay-` | 接收端 | Android 6 / API23 | Standard 接收能力 + 手动开启苹果系统镜像，含 GPL 模块；`dev.lancast.receiver.airplay` |

**四个 APK 是四种产品，不是四种 CPU 架构。** 默认每个 APK 都含 ARMv7a 与 ARM64；单 ABI 发行仍是后续发布目标。三个接收变体按需求选一个即可，AirPlay 版包含基础接收功能，不必再安装 Standard。它们使用不同应用 ID，安装后的名称也分别标注 Standard、Legacy、AirPlay。

Android 手动页面的“产品”可选全部、发送端、全部接收端或某个接收变体。PR/`main` 自动构建默认全选。选择只接收时不编译发送 TS/FFmpeg；只有 AirPlay 被选中才构建对应 JNI、生成 GPL 源码材料。Standard 与 AirPlay 使用相同 Rust 控制 feature，每个 ABI 只编译一次再分配给两个变体。基础原生与 AirPlay 缓存分开，缓存包含产品选择、ABI、工具链/源码输入，不把另一组产品的旧缓存当作本次结果。

## Apple TV 与 Apple 下载包

tvOS 工作流构建 `LanCastTV`，提供 LanCast 自有 WSS/WebRTC 镜像与 MP4 接收。Rust 仅开启接收所需 `legacy` HTTPS 媒体桥；Xcode 目标排除 SenderModel、SenderSession、BroadcastStore，界面只有接收功能。共享 RTC 供方框架仍是通用二进制，本轮不声称已经删除其中所有编码器代码。

| 下载名前缀 | 内容 |
|---|---|
| `LanCast-tvOS-Receiver-` | 接收端 Device 和 Simulator 两份 App 压缩包 |
| `LanCast-iOS-Sender-Receiver-` | iPhone/iPad Device 和 Simulator 两份 App，含广播扩展 |
| `LanCast-macOS-Sender-Receiver-` | Intel/Apple Silicon 通用 App |
| `apple-<platform>-build-reports-` | Xcode 工程快照、元数据和 macOS 测试结果，供开发审查 |

**Device 和 Simulator 是设备/模拟器目标，角色相同。** Device App 需要自行签名才能安装；Simulator App 只能在对应 Xcode 模拟器运行。tvOS 工作流没有构建 Android 的可选 AirPlay 模块；它与 Apple TV 系统自带 AirPlay 也是不同入口。

每个平台的目录和压缩包名都由 `apple_products.py` 明确指定；构建只取本次配置要求的目标，缺任何一个就失败，不再扫描所有旧配置目录。用户包保留 App、许可证、安装说明、哈希/构建报告；测试宿主、Xcode 工程和 xcresult 放进审查产物。三个 Apple 工作流均在上传前运行离线包校验，检查实际身份、版本、架构、设备/模拟器类型和 iOS 扩展；tvOS 另检查 Apple TV 设备家族且不含广播扩展。

## 手动参数与版本

在所需 Actions 页面点击 **Run workflow**，通常选择 `Branch: main`，文本框留空；Android 再按用途选择产品。不同参数的运行使用不同取消分组，重复同一组才取消旧运行。

| 参数 | 填写方法 / 作用 |
|---|---|
| `product`，仅 Android | 默认全部；选择发送端、全部接收端或一个接收变体 |
| `source_ref` | 一般留空；可填分支、标签或完整提交号，决定实际编译源码 |
| `version` | 一般留空；覆盖时填 `0.6.1` 这样的三段数字，每段 0–9999 |
| `build_number` | 一般留空；覆盖时填 1–65535 的整数；Android 升级需大于已安装版本且使用相同签名 |
| `configuration` | Windows/macOS 默认 Release，其余默认 Debug；中文选项对应原生 Debug/Release |

Android Debug 是开发签名包，不同 GitHub runner 的临时调试密钥不保证相同，跨运行覆盖安装仍需核对签名。Android Release 为未签名优化包。iOS/tvOS Device 两种模式均未签名；macOS 不自动公证。选择 Release 不会发布商店或 GitHub Release，页面“日常使用”不表示正式发行验收完成。

源码分支选择控制工作流定义，`source_ref` 控制应用源码；历史源码必须实现所选工作流要求的脚本接口，否则应使用历史工作流。手动输入通过结构化 API/环境变量传入，并在执行构建前校验，不拼进 shell。PR 通常检出合并测试提交；Actions `head_sha` 与产物中的 `source_commit` 可以不同，以产物报告为实际源码证据。

版本号写入 Android versionName、Apple CFBundleShortVersionString、Windows ProductVersion，构建号写入对应包元数据。Python 参数优先于 `LC_VERSION` / `LC_BUILD_NUMBER` / `LC_CONFIGURATION` 环境，最后才用 `build-config.json`；Android ABI 由配置或 `LC_ANDROID_ABIS` 选择。构建后的 APK、Info.plist、PE 元数据必须与本次配置一致。

## 脚本调用与产物校验

```sh
# 在 GitHub 构建一个 Android 接收端；其余参数由远端源码默认值决定
python scripts/github-ci.py --dispatch --workflow android.yml --ref main --product receiver-standard
python scripts/github-ci.py --dispatch --workflow tvos.yml --ref main
python scripts/github-ci.py --dispatch --workflow airplay.yml --ref main

# 查询指定提交的全部工作流；缺失项会明确显示 missing
python scripts/github-ci.py --all --sha <工作流提交的完整SHA>
python scripts/github-ci.py --workflow android.yml --sha <完整SHA> --artifacts
python scripts/github-ci.py --run <run-id> --failed-logs
python scripts/github-ci.py --run <run-id> --download <artifact-name>
```

`github-ci.py` 支持全部八个入口、日志和分页产物；省略版本/配置时不再把本地默认值覆盖到远端旧版本。复用 `GH_TOKEN` / `GITHUB_TOKEN` 或 Git 凭据，凭据仅在内存，下载重定向移除 Authorization，保存日志时脱敏。这个工具只负责 GitHub 操作，不被应用运行代码依赖。

完整 Android 本地构建要求 JDK17、SDK36/Build Tools35.0.0、NDK27.2.12479018 和 Rust1.98.1；设置 `ANDROID_HOME`、`ANDROID_NDK_HOME` 后运行：

```sh
chmod +x android/gradlew  # Linux/macOS；Windows 使用 gradlew.bat，无需此步
python scripts/build-android.py --native --product receiver-standard
python scripts/build-android.py --native --product all --version 0.6.1 --build-number 9 --configuration Debug
python scripts/verify-apks.py --product receiver-standard
python3 scripts/build-tvos.py --configuration Debug  # 必须在 Mac/Xcode 上
```

`--native` 自动准备所选 JNI；不加时复用已准备好的 JNI，Actions 通过缓存完成此步骤。产品入口会在同一有效配置下完成 assemble、lint、所需 JVM 契约、依赖隔离、APK 校验与打包，无需另传一次自定义版本才能校验。独立 `verify-apks.py` 也接受相同参数；复查自定义构建时应传相同版本、模式与产品。

APK 校验逐个核对应用 ID、显示名称、最低 SDK、版本、角色服务、ABI、GPL/TS 隔离及每个 JNI 库的真实 ELF 架构/加载段对齐；拒绝漏产品、重复旧 APK 和额外不合格 native 库。仅验证成功后上传用户产物；失败时可上传报告，不把残留 APK 当成功交付。产物内的 manifest 记录角色、签名边界、源码、字节数和 SHA-256。

## D16 构建模块与维护边界

| 模块 | 单一职责 |
|---|---|
| `build_config.py` | 共享版本/模式/ABI 校验、有效配置与源码记录 |
| `android_products.py` | Android 产品身份、选择、角色、Gradle 任务和 Rust features |
| `android_ndk.py` | 两个独立 Rust 工作区共用的 NDK 编译环境 |
| `android_artifacts.py` | 产品及 ELF 校验、按角色打包；不负责触发编译 |
| `apple_products.py` / `apple_build.py` | 前者定义角色和交付目标，后者执行依赖准备、Xcode 构建与明确目标打包 |
| `github_api.py` / `github-ci.py` | 前者只做凭据/HTTP/分页，后者组合 Actions 查询、触发与下载 |

新增产品先扩展产品清单和角色契约，再接 Gradle/Xcode 目标、工作流选项/上传与文档。测试约束选项同步和职责隔离，真实包检查负责发现构建配置漂移。CI 编排不实现业务协议，App 不导入构建模块，控制核心也不依赖可选 GPL 库。正式签名、单 ABI 发布、供方 RTC 源构建和完整二进制 SBOM 仍按[06](06-开发计划与验收.md)独立验收。
