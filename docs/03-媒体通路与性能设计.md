# 03 媒体通路与性能设计

## 1. 共同采集与编码前段

来源在本机选择：Windows全屏或窗口；Android10–13全屏、14+系统单应用分享；Mac由ScreenCaptureKit选择窗口或显示器，iOS按ReplayKit允许的广播来源。Apple共享H.264/Opus路径与平台限制见D09。受保护画面、音频禁采、最小化/关闭窗口须明确处理，不承诺绕过系统限制。

CaptureSession拥有一次授权和对应平台资源。按选定路由连接RTC媒体适配器或DLNA直播适配器；一次只运行一个录屏/声音源。共享接口和配置并不要求同时复用一个已启动的编码器对象。

H.264默认硬件编码；平台不支持时先降低分辨率/帧率再重试有限次，仍失败返回不支持，不捆绑大型软件编码器作隐蔽兜底。接收端硬解失败也不能无限软件解码导致老电视过热。

GPU/Surface输入优先，避免屏幕→CPU RGB→YUV→GPU来回搬运。编码选择SDR BT.709、保持比例、限制队列、禁用B帧；只有系统编码器确实接受并报告参数时才显示该档位已启用。

## 2. 自有WebRTC镜像

```text
平台捕获 → H.264硬编码 ┐
系统声音 → Opus编码    ├→ WebRTC/RTP/SRTP → 自有接收 → 硬解/播放
                      ┘
```

按D08，Android使用libwebrtc，Windows用libdatachannel处理SDP/ICE、RTP/RTCP和SRTP，不自行重写RTP。Windows已接入SR/NACK/PLI/REMB，但不能将其等同于已经完成libwebrtc整套拥塞控制的性能验收。只配置局域网直连，不依赖默认公网STUN/TURN；隔离网络不通时说明AP/VLAN/防火墙原因。

视频与音频来自共同单调时基；RTP时钟频率不同，不直接比较时间戳数值。同步通过媒体引擎/RTCP映射处理。系统音频默认关闭语音通话型AEC/自动增益等处理，避免改变音乐/视频音质；不混入麦克风。

Standard起步1080p30约6Mbps（能力不足降720p）；Legacy起步720p30约3Mbps。1080p60仅对硬编硬解和网络余量通过的设备开放。先由WebRTC调码率，持续5秒低帧率/积压才降档，稳定30秒且有余量再升档，防止反复震荡。

## 3. DLNA桌面直播

```text
屏幕/窗口 → H.264 ┐
系统声音 → AAC-LC ├→ MPEG-TS → 连续HTTP → 电视已有DLNA播放器
                 ┘             ↑
                       UPnP SetURI / Play / Stop
```

DLNA负责发现和控制；HTTP资源持续生成而非必须事先保存。PPT翻页、窗口变化都成为直播中的新画面。此路径无需电视安装我们的App，但要求其接受相应codec/TS/HTTP响应，电视预缓冲仍可能增加延迟。

首版固定配置：720p30、H.264兼容profile/level、3Mbps、GOP1秒、B帧0，AAC-LC48kHz/128kbps，默认双声道；1080p30/6Mbps作为经验证档位。GOP可0.5/1/2秒，不能把GOP值当端到端延迟。Opus编码结果不能直接换个容器供DLNA使用，需要从PCM选择AAC分支。

共享TS封装层接收H.264 Annex-B access unit、raw AAC及AudioSpecificConfig、共同PTS，FFmpeg最小子集负责封装与交织；不启动ffmpeg子进程，不录像到磁盘再读取。

编码器keyframe标志不足以证明可起播，必须确认实际SPS/PPS/IDR。mux输出的安全起点包括PAT/PMT、codec配置和IDR；处理AAC交织导致IDR稍后才真正输出的情况，不能错误标记上一个空/非随机访问块。

## 4. 时间戳与缓冲规则

媒体接口统一微秒；相对会话起点使用单调时钟。AAC时间来自采样位置，不能靠墙钟或定时器每次简单加10ms推算。重采样、编码延迟和不连续采样由媒体层显式校正，不能靠持续加大缓存掩盖漂移。

| 队列 | 硬上限与行为 |
|---|---|
| 原始视频 | 最多2帧，允许丢弃过时原始帧 |
| TS全局保留 | 最多2秒且≤8MiB，任一超限即裁到合法边界 |
| 单订阅者 | 最多1MiB，过慢则断开该订阅者，不拖累所有人 |
| 单次跨FFI写入 | ≤65424字节（188字节的整数倍），非阻塞入队 |
| 起播等待 | 最多8秒，未获得安全起点则结束启动 |

不能随意丢已编码P帧/半个GOP后继续宣称流可解码。需要丢弃时停止旧订阅、请求新IDR，从完整起点恢复。缓存上限不是固定播放延迟；新GET默认等待下一合法起播点，不把几秒旧桌面全量补发给电视。

AirPlay独立接收队列的24帧/8MiB/300ms视频与64帧/1MiB/500ms音频预算、配置/乱序时间戳、通知等待、关闭及解码资源所有权见[D17](21-AirPlay媒体队列与资源生命周期.md)。这些编码队列上限不包含平台解码器和音频输出缓冲；实际RSS/CPU与同步仍需分别测量。

## 5. 文件与直播HTTP

| 项目 | 文件 | 直播 |
|---|---|---|
| MIME | 真实video/mp4 | video/mpeg，与DIDL一致 |
| 长度 | 真实Content-Length | 不伪造固定Content-Length |
| Range | 单段206，越界416，HEAD正确 | 忽略Range并返回200新直播；不提供DVR |
| 暂停/seek | 依播放器支持 | 首版只支持停止/重新开始，不积压旧桌面 |
| 地址 | 会话授权的文件资源 | 会话授权的连续流资源 |
| 生命周期 | 文件/会话结束撤销 | 停止录屏/断线预算耗尽立即撤销 |

直播默认HTTP/1.1 chunked。仅接收器档案验证需要时使用HTTP/1.0 close-delimited：无CL/TE、Connection:close。两者都要测试，不使用伪造超大文件长度骗过电视。多段文件Range首版可忽略并返回200；416附正确总长度信息。

HTTP仅绑定选定LAN接口，URL使用电视可达地址。每资源至少128bit随机token、绑定目标IP、无目录列表、无任意文件路径/URL代理。自有文件通道使用HTTPS与配对身份；DLNA通常使用兼容HTTP，明确媒体未受SRTP保护。

## 6. DLNA控制流程

1. SSDP有限扫描MediaRenderer/AVTransport；核对UDN与设备描述。
2. 解析设备实际声明的serviceType/controlURL；禁止DTD/外部实体、跨设备/公网重定向和凭据URL；响应大小及深度受限。
3. GetProtocolInfo作为线索，不能把空值当永久失败或把广告值当实测成功。
4. 绑定HTTP、启动捕获、等待合法TS起播点，生成LiveMpegTs资源描述。
5. SetAVTransportURI后Play；文件/直播不能共用硬编码MP4的DIDL。
6. 观察电视GET及GetTransportInfo，10秒内完成启动判定；无法观察首帧时firstFrameMeasured=false。
7. 每2秒查询，连续3次失败/停止触发结束或一次受控恢复。Stop是best-effort，撤销本地资源和采集是必须成功的清理动作。

读查询允许一次重试；写操作超时可能已经执行，先查状态，不直接重复播放。metadata/MIME/后缀/protocolInfo与真实资源保持一致，不填写未经确认的DLNA profile。设备差异放在有版本的ReceiverProfile适配表中，不散落于UI和业务逻辑。

## 7. 文件直放与Legacy安全桥

已有MP4优先原文件播放，不走录屏重复编码。Standard的Media3使用受控数据源验证已配对发送端的TLS身份；Legacy系统MediaPlayer不能直接配置同等的每连接SPKI校验时，使用可选的本机媒体桥。

Legacy媒体桥只监听127.0.0.1，为一个已授权远端资源提供随机token的Range端点；上游由Rust HTTPS客户端校验发送端身份。它不是任意URL代理，不接受外部入站、任意目标地址或本地目录。使用≤256KiB流式缓冲，结束撤销。该模块只打包到Legacy接收版，不影响RTC路径或其他客户端。

Legacy只承诺基础MP4/H.264/AAC及普通seek，不承诺精确到帧或复杂容器。系统播放器不兼容的机型按实际测试限制；不能通过关闭TLS校验来解决自签证书问题。

## 8. 诊断与性能证据

分别记录采集fps、编码耗时/丢帧、实际codec/profile、码率、缓冲时间、HTTP拉流、电视报告状态和本机资源量。日志不记录原始画面/声音、完整token、文件私有路径或敏感请求头。

RTC的RTT、TS缓存长度、GOP、SOAP PLAYING都不是端到端画面延迟。用合成时钟/闪光/点击声和外部拍摄或采集卡测量；区分发送端、网络、接收器预缓冲和电视显示后处理。性能目标只在[验收文档](06-开发计划与验收.md)定义。
