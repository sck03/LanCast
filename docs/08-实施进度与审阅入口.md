## 架构映射

| 模块 | 已落实边界 | 维护注意点 |
|---|---|---|
| domain / core | 无 I/O 的能力、授权、代次与路由规划 | 通用 Coordinator 尚未替代 WSS 全部状态；不能仅凭目录宣称全面收口 |
| adapters | WSS/TLS、发现、文件、UPnP、直播协调、设备档案分别成模块 | Runtime 是命令组合入口，新增用例应委托专用模块 |
| ffi | 整数句柄、版本化 create_v2、非阻塞 shutdown、独立 TS 入口 | 旧 create 兼容；宿主不能自行释放 Rust 缓冲 |
| media-native | 固定 FFmpeg 最小 TS 封装、H.264 SPS/VUI 修正，C ABI/JNI | 无软件编码器、解码器、网络或整包 FFmpeg 程序依赖 |
| windows/media | 采集、GPU 转换、H.264/AAC/Opus、声音、RTC、TS 输出分离 | 全部编码工作留在专用线程，只有编码后的 TS 交给 Rust |
| Android | 授权/前台服务、RTC、DLNA、播放器接口分离 | Standard Media3；Legacy 系统播放器和 TLS 上游桥 |

## 验证记录

本轮本地 Windows 的 Rust 工作区测试与全 feature/all-targets clippy 通过。提交 2cca13a 的原生作业已验证真实合成 TS：三个中途加入位置、四种 PSI/PES 重分片边界，以及生产 HTTP/UPnP 到模拟电视闭环，输出再由 FFmpeg 解码。HTTP 覆盖 1.0 close-delimited、1.1 chunked、HEAD、Range 连续流策略、Load/Play/Stop 和撤销。

程序提交 [c214877](https://github.com/sck03/LanCast/commit/c2148776b10c9ec3bf5c54f438eea7f080cfe430) 的[完整流水线37121341166](https://github.com/sck03/LanCast/actions/runs/37121341166)全部通过：Rust双平台、TS/真实H.264元数据与HTTP闭环、Android三个APK/lint/ABI、Windows编译/RTC回环/DLL反复卸载/PE依赖，以及两平台原生源码和重链接材料归档。

Windows rtc_contract 验证本机ICE/DTLS/SRTP、H.264/Opus RTP、旧协商拒绝和关闭；media_abi_contract验证反复load/create/stop/unload和销毁后无回调。原始C API回调不假定自动等待：自有适配用整数token和回调锁，删除实例后迟到回调找不到owner；卸载前等待RTC全局线程退出。

对同一提交的CI产物，本机RX580另行生成2,388,352字节合成TS，确认1280×720 H.264 Constrained Baseline/BT.709、48kHz双声道AAC、正确三色与440Hz提示音。173个视频包的PTS=DTS且严格递增，跨度5.736秒；这不是端到端延迟测量。9个中途加入/分片/HTTP输出均用原始时间基解码，无诊断错误。详见[实际复查方法](10-构建与合成验收记录.md)及[机器记录](validation/rx580-c214877.json)。

本机未配置完整VS/Android SDK，也没有本任务可使用的真实电视。主机为低于WGC基线的Windows LTSC1809，合成硬编通过不代表该系统的窗口捕获已获支持。延迟、音画同步、完整GPU矩阵、两小时长稳和受限电视兼容率仍未验收；按06逐项填写真实结果。
