# 08 实施进度与审阅入口

日期：2026-10-03。**开发快照，未完成完整v1.0，不能用于宣称三条媒体路线已经交付。**

## 架构映射

| 模块 | 实现入口 | 已落实边界 |
|---|---|---|
| cast-domain | crates/cast-domain | 无I/O；类型、能力证据、媒体端口 |
| cast-core | crates/cast-core | 纯路由规划、授权/探测/代次/停止状态机；可替换媒体端口 |
| cast-adapters | crates/cast-adapters | WSS身份、发现、UPnP、Hyper文件/直播服务、Legacy桥 |
| cast-ffi | core | 保留liblancast_core库名兼容JNI；整数句柄、异步shutdown、独立TS入口 |
| media-native | media-native/ts | LGPL最小FFmpeg封装；C ABI与JNI不暴露AVFormatContext |
| Android | android | Kotlin；Standard Media3与Legacy系统播放器独立依赖；媒体与UI模块分开 |
| Windows | windows/src | Win32文件/控制客户端；显式C ABI媒体库适配入口，无必需GStreamer |

当前应用用例尚未全部接入cast-core：WSS协议会话仍由adapters/session维护，Android发送组合仍在SenderRuntime。不能仅凭四个crate目录就宣布完成解耦。下一步是以会话事件/端口替换这些组合层中的重复状态，而非继续往Runtime增加平台分支。

本机没有可用VS2022 CMake实例，Android SDK不在现有配置中。完整平台构建由Actions执行。没有实机测试，因此包体目标、延迟、音画同步、2小时长稳和电视兼容率全部仍为未验收。

## D07 开发快照的明确差异（不是更改v1.0目标）

1. Android临时继续使用固定io.github.webrtc-sdk:android:150.7871.01，删除了根据本地文件是否存在自动替换AAR的行为。自建输入必须通过lancastWebrtcAar显式指定。只有完成源版本、产物哈希和裁剪验证，才能作为v1.0发布输入。
2. Windows旧GStreamer媒体实现移到experimental-gstreamer供迁移参考，不参与默认构建/打包。默认客户端可运行文件流程，但没有屏幕媒体后端；不捆绑大型运行时掩盖缺失功能。
3. Android直播试验入口仍不满足“先合成Probe后真实屏幕”的正式产品流程，不自动写入passed能力，不得发布为已支持设备通路。
4. XML沿用已有限制的roxmltree解析器，功能是受限设备描述/控制解析，不引入第二个XML运行时；正式依赖变更评审时统一到目标清单或接受该差异。
