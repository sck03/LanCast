# 29 会话就绪与能力模块重构

日期：2026-11-20；应用版本0.8.0 / build 42。本文替代此前文档中关于文件按钮就绪、Rust feature、Android文件FD和Windows事件轮询的描述。旧版本应用接口与存量数据无需兼容；Android Legacy仍是一个受支持的旧系统产品名称，不代表旧LanCast协议兼容层。

## 状态和资源所有权

- 自有文件：选择/准备 → 建立会话 → file.load → 接收端session.state=ready → 可控制。ready必须匹配当前会话；reload或loading立即撤销可控制状态。Windows、Android、Apple统一使用此条件，不再把file.shared或选择文件视为播放就绪。
- Rust发送端对提前播放命令产生command.rejected（PLAYBACK_NOT_READY，含requestId/sessionId），接收端也校验Playing状态。文件初始就绪期限20秒，重复loading不延长期限；ready解除期限；超时发session.stop/FILE_LOAD_TIMEOUT并清理。UI不排队重放过期用户命令。
- Android FileShare持有唯一文件请求、状态和取消信号。系统文件选择结果绑定原始目标和请求ID。FileShareService以connectedDevice前台服务承载LAN文件连接，和mediaProjection录屏服务分别声明。服务在前台建立后才开始provider读取；后台线程数1、排队数1、空闲线程自动回收。provider读取期限30秒，文件就绪期限20秒；停止、断连、服务销毁或过期结果均释放文件。
- JNI shareFile借用ParcelFileDescriptor并在Rust入口复制一个拥有的FD；原句柄始终由Kotlin use关闭。队列拒绝、无效handle、关闭、取消和过期命令由RAII关闭副本。删除JSON裸fd转交约定，避免Java预检查失败或原生队列拒绝时所有权含糊。
- Android/Windows的扫描完成、超时和停止使用各自单一收尾函数，立即解除扫描状态/多播锁，并提升generation拒绝旧结果。停止操作不等待25秒的搜索兜底。搜索失败和“未发现设备”分别显示。

## 平台性能路径

- AirPlay MediaCodec暂时无输入缓冲时保留一个待提交帧，同时继续排空输出；音视频分别使用固定500ms拥塞预算。关闭可中断重试，队列仍受原数量/字节/时间上限限制；不会任意跳过H.264参考帧。INFO_TRY_AGAIN_LATER本身不再触发整路停止。
- Android TS输出由C++同步NewDirectByteBuffer借用mux数据，Rust验证容量后直接送入有界直播资源，只有最终Bytes存储保留一份复制；不再经过Java ByteArray和Rust临时Vec。Sink不得保存buffer；回调返回即结束借用。JNI/R8签名同步更新。
- macOS ScreenCaptureKit音视频回调使用专用串行队列。队列拥有活动SCStream与固定回调快照；主线程停止先同步关闭交付，控制/UI继续在主线程。SenderSession的媒体引用由锁保护，RtcSession继续负责有界样本队列。
- Windows CoreEvents独立拥有阻塞wait_poll线程与最多32条待交付事件；UI消息消费后才继续读取下一批。核心切换/销毁先唤醒并回收等待线程，避免旧handle事件污染新连接。500ms计时器仅保留扫描/退出/DLNA状态期限，不再50ms轮询Rust事件。
- Windows H.264用MFTEnum2及MFT_ENUM_ADAPTER_LUID选择与采集D3D11设备同一GPU的硬件候选；每个候选必须完成D3D11支持、DXGI manager、codec属性、媒体类型及启动验证。失败释放该候选并继续，最终保留具体错误。

以上是确定的分配/复制/唤醒路径变化。未测量CPU、RSS、端到端延迟提升比例，也未把CI无GPU环境视为混合显卡真机验收。

## 构建能力与依赖

| Rust feature | 能力/使用产品 |
|---|---|
| none | 自有WSS/RTC控制、mDNS；Android Standard/AirPlay基础接收核心 |
| file-sender | 文件资源及HTTP服务；Apple发送端 |
| dlna | SSDP/AVTransport客户端及XML解析 |
| dlna-live | dlna + file-sender + 有界TS直播/测试档案 |
| sender | file-sender + dlna-live，Windows/Android发送端组合 |
| file-proxy | 固定指纹HTTPS到loopback的播放器代理；Apple/tvOS与Android Legacy |
| http-server | 文件发送/代理内部共享连接能力，由上层feature启用 |

Apple macOS/iOS使用file-sender,file-proxy，tvOS只使用file-proxy；删除legacy Cargo feature和legacy_bridge模块旧名。roxmltree/reqwest/HTTP服务依赖按能力选择。ProfileStore仅测试使用的open/save便捷包装限制为cfg(test)。PinnedHttp和OkHttp从control-bridge移到player-standard，不再让发送App因控制模块依赖播放器HTTP库。

删除session.start.audioRequested和file.load.mediaId/durationMs生产字段；音频由实际媒体配置控制，file.load只传实际资源描述。保持窄边界，不为未来猜测功能增加空转接口。

## DLNA与AirPlay技术核对

2026-11-20直接核对官方文档与GitHub上游API：

- OCF公开MediaRenderer:3与AVTransport:3标准；它们是已有标准，不是2026年新发明的低延迟协议。本轮按设备宣告选择最高已支持的AVTransport 1–3，保留实际serviceType发送SOAP；忽略畸形和未知服务版本。SSDP查询MediaRenderer:1仍用于发现兼容的真实电视，不能按本应用“不兼容旧数据”的要求移除第三方协议基础互通。支持新版本描述并不等于实现AVTransport:3所有可选动作。
- Windows/Android现在消费结构化dlna.state，区分load接受、电视transportState和播放position。Windows低频交替查询，Android在初始加载时查询状态并提供手动进度查询。只读状态查询失败不撤销正常文件资源；不自动重试Play/Seek等写操作。firstFrameMeasured仍为false，电视报告PLAYING不证明屏幕首帧或延迟。
- rairplay上游HEAD仍为7a0ec4036905afe0c8de16881d85d5846dc938a7（2026-07-20），与vendored基线一致，未发现可直接更新的新发布。保留现有本地修正、来源哈希和独立GPL工作区。
- UxPlay当前发布v1.73.7（2026-09-04）；HEAD 48f5ce47c9ef694afccfac907c9e8828329657fe（2026-11-17）增加FairPlay v2相关支持；其发布说明列有镜像、音频和YouTube HLS等功能，渲染使用GStreamer。不能据其产品名推断本项目已经支持所有AirPlay 2能力，也不为旧FairPlay支持替换当前Android MediaCodec管线。
- Shairport Sync 5.6.3（2026-11-10）提供音频接收修正，不能代替屏幕镜像接收器。Apple官方还描述Bonjour、蓝牙发现与点对点AirPlay；这些不等于给第三方Android库开放完整系统接收SDK。多房间、DRM视频、HLS URL播放和Apple Home不纳入本轮实现。
