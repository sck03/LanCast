# 02 模块架构与接口契约

本文件是目标模块边界和接口合同。实际映射与未接通部分见08；当前四个Rust crate已建立，业务协调器尚未覆盖所有平台流程。

## 1. 分层及允许的依赖方向

```text
应用组合层（Android / Windows / Apple）
        ↓
应用核心：会话协调、用例、权限结果、路由选择
        ↓
领域模型与端口：意图、设备证据、配置、状态、接口

协议/平台/播放器/存储适配器 → 实现端口
媒体原生库 → 实现媒体端口，不反向依赖应用界面
```

领域层不引用Android、Windows、libwebrtc、FFmpeg、HTTP服务器或UI类。应用核心只依赖领域模型和端口。适配器依赖端口和具体库；组合层负责实例创建、配置、生命周期和编译功能选择。

网络消息模型不能直接充当UI状态或数据库实体。边界转换显式完成，避免修改一个协议字段就影响所有模块。模块之间不通过共享全局变量、任意JSON对象或单例相互探测。

## 2. 初始模块，避免过度拆分

| 模块 | 职责 | 允许依赖 | 禁止职责 |
|---|---|---|---|
| cast-domain | Intent、Route、Capabilities、Profile、状态、错误码 | 标准库/小型数据定义 | I/O、平台API、线程调度 |
| cast-core | 会话协调、路由、取消/重试预算、播放用例 | domain、端口 | 直接调用MediaCodec、拼SOAP、操纵View |
| cast-adapters | WSS/TLS、mDNS、SSDP/UPnP、HTTP文件/直播、设置存储 | core端口、所需开源库 | 业务决策或自动开启未经同意的采集 |
| cast-ffi | C ABI、事件分发、句柄、JSON边界验证 | core、按feature注册的adapters | 编解码、逐像素转换 |
| media-native | 共享最小TS封装、H.264元数据修正与C ABI/JNI | 最小FFmpeg、标准库 | UI、发现、采集或完整RTC实现；平台RTC与采集分别在windows/media、Android媒体模块和Apple Shared/Media |
| Android平台层 | Kotlin权限、前台服务、MediaProjection、MediaCodec、播放器 | FFI、平台媒体接口 | 复制一套Rust会话/网络实现 |
| Windows平台层 | C++原生UI、平台事件、媒体桥 | C ABI/媒体C ABI | 在窗口事件函数中实现整个会话状态机 |
| Apple平台层 | SwiftUI、采集授权、独立广播扩展、AVPlayer/Metal | CoreSession、RtcSession、纯Swift Contracts | 复制TLS/发现实现、媒体层反向引用UI；详细边界见D09 |

物理Rust crate先保持domain/core/adapters/ffi四个，adapters内部按模块划分；只有出现独立发布、依赖冲突或团队边界才再拆crate。避免为每个小接口建立一个工程，也避免一个核心模块吞下全部平台实现。

Windows媒体按capture/encoder/audio/rtc_channel/ts_output/backend划分；公共边界使用C ABI，媒体库内部同工具链使用自有类型。外部应用不持有RTC库对象、FFmpeg上下文或STL容器。D08将Windows RTC改为libdatachannel，Android保留固定上游AAR。

D16将构建产品身份、构建执行、产物验证和GitHub操作分离，详见[13构建模块边界](13-独立平台构建与版本配置.md#d16-构建模块与维护边界)。Android一个发送端/三个接收变体、tvOS仅接收由明确产品清单约束；Gradle/Xcode目标及真实包校验共同验证角色。构建模块不进入应用运行依赖，GPL协议仍独立于共享控制核心。共享供方RTC库尚未完成按角色的二进制裁剪，不能将角色隔离等同于完整源码裁剪。

## 3. 核心数据模型

| 模型 | 必需信息 |
|---|---|
| Intent | mirror或file；来源选择由本机用户决定 |
| DeviceIdentity | 本地id、DLNA UDN或自有设备id、名称、地址/接口、型号/固件、发现来源 |
| DeviceEvidence | rtc、dlnaFile、dlnaLive各自unknown/passed/failed；测试配置/时间/证据来源 |
| Installability | installed/store_available/blocked/unknown；不能由Android版本推断 |
| BackendAvailability | 当前构建包含且初始化探测通过的RTC/TS/文件能力 |
| RoutePlan | webrtc_mirror/dlna_live/receiver_file/dlna_file/system_guide；use/probe/unavailable及原因 |
| VideoProfile | H.264 profile/level、尺寸、fps、bitrate、GOP、色彩、旋转/比例策略 |
| AudioProfile | Opus或AAC-LC、采样率、声道、bitrate、是否请求音轨 |
| Session | UUID、owner、intent、route、device、generation、资源句柄、状态、deadline |

设备能力、本机实现能力、用户授权、实测性能四项独立。RoutePlan的use仅表示选定通道，不能绕过后续授权和初始化。

## 4. 端口接口职责

| 端口 | 操作及事件 | 实现方 |
|---|---|---|
| DiscoveryPort | scan/cancel、deviceFound/expired | mDNS与SSDP适配器 |
| PairingPort | pair/cancel/revoke、approvalRequested/accepted/rejected | TLS/会话身份适配器及平台确认UI |
| CaptureConsentPort | request、granted(handle)/denied/revoked | Android/Windows/Apple平台层 |
| MediaSessionPort | start(profile,grant)、reconfigure、requestKeyframe、stop、stats/error | 原生媒体层 |
| RtcPort | offer/answer/ICE、connectionChanged | Android libwebrtc、Windows libdatachannel、Apple RtcSession适配器 |
| LivePublisherPort | create、writeTs、startPointReady、subscriberObserved、revoke | Rust HTTP直播适配器 |
| RendererControlPort | load(resource)、play/pause/seek/volume/stop、state | 自有控制或DLNA适配器 |
| FilePlayerPort | load/play/pause/seek/volume/stop、ready/ended/error | Android Media3/Legacy系统播放器、Apple AVPlayer与固定上游桥 |
| DeviceProfileStore | load/save/invalidate、schemaVersion | 本地非敏感设置存储 |

不设计一个含几十个可选方法的万能Transport接口。RTC协商、DLNA控制、文件播放器各有具体端口，应用核心在协调器内组合。不同能力由Capabilities声明，未支持的方法返回明确错误而非静默空操作。

[D15](18-AirPlay按需接收设计与接入方案.md)已以独立`airplay-native` Cargo工作区、`:airplay-receiver` Android库和纯Kotlin`:receiver-contracts`接入，模块映射见[20](20-AirPlay实现与审阅指南.md)。待确认和活动播放都经过同一租约；原生协议通过窄JNI直接交付编码媒体，UI不解析协议。该域契约放在Android宿主侧，避免两个独立JNI库分别维护“空闲”状态；现有Rust控制核心不依赖GPL协议库。AirPlay认证、AAC-ELD、时钟与关闭流程独立，不套用WSS认证或RTC恢复。现代/旧路径的实际设备验收另行记录。

[D17媒体资源合同](21-AirPlay媒体队列与资源生命周期.md)进一步明确：纯Kotlin队列负责完整时间跨度、容量及关闭唤醒；平台播放线程独占解码器/音频输出，初始化成功才转移所有权。关闭与入队使用同一同步边界，编码媒体不经UI或控制JSON。

[D18 HTTP生命周期](22-HTTP生命周期与直播分发.md)由`http_server`统一拥有最多四个连接任务，并负责退出等待和每连接取消；文件、直播、固定上游桥继续各自实现资源策略。`live`的私有订阅状态拥有起播门控、时间预算与接收通道，稳定分发复用入口已校验的`Bytes`，平台层不参与这些网络状态。

## 5. 状态机

公共阶段：Idle → Preparing → Authorizing/Probing → Starting → Active → Stopping → Idle；错误经过Stopping释放，不能绕过清理。

- RTC内部：Pairing → Negotiating → Streaming，可在有效授权及15秒总预算内Recovering。
- DLNA直播内部：CreatingResource → StartingCapture → WaitingForRAP → LoadingRenderer → ConfirmingPull → Streaming。
- 文件内部：PreparingResource → LoadingPlayer → Playing/Paused；seek是命令，不另建会话。

会话取消令牌覆盖所有I/O和媒体等待。用户停止/系统撤销最高优先级，先取消和解除阻塞，再等线程退出。相同stop可重复调用。迟到回调按sessionId+generation丢弃，不能更新下一会话的UI。

WSS 的实现边界、停止任务屏障、配对关闭事件与架构检查见[D11](14-控制连接生命周期与维护边界.md)。Runtime不直接持有或修改WSS会话表。

直播恢复至多一次自动重建电视播放；RTC恢复至多三次退避1/2/4秒，所有等待含在15秒总预算内。预算耗尽结束；原采集授权已失效时禁止自动重新录屏。视频文件断点续播与屏幕直播恢复是不同策略。

## 6. 线程和内存所有权

- UI线程只处理交互、权限与显示，不等网络、codec或线程join。
- Rust一个受控运行时负责控制网络；每会话状态由单一actor/串行任务修改，避免多个锁相互等待。
- 采集、编码、渲染使用平台/媒体库的专用线程；实时回调不做磁盘日志、DNS、JSON大对象或等待电视。
- 原始像素保持GPU/Surface路径，不穿过Rust或JNI做重复CPU拷贝。
- 编码后的TS跨FFI允许一次有界复制；不为几Mbps编码流引入复杂的跨语言共享内存所有权。
- 所有队列有字节/时长上限，媒体队列与控制队列分开。停止命令不能排在数秒媒体之后。

回调数据只在回调期间有效，异步保存必须复制。销毁不能在自身回调线程同步等待该回调结束；提供异步shutdown完成事件，再释放最终handle。Rust panic和C++异常不得跨C ABI。

## 7. C ABI与事件协议

公共ABI固定使用C兼容整数、长度、只读字节片段和opaque handle；不传STL、Rust引用、Kotlin对象或codec内部结构。所有结构含size/abiVersion，新增尾部字段可兼容，改变语义提升major版本。

控制入口概念：create(config,callbacks)、submitCommand(handle,request)、shutdown(handle)、release(handle)。TS使用独立writeTs(streamHandle,bytes,length)入口，不通过JSON/base64。返回ok/closed/backpressure/invalidInput，不在同步返回中等待网络完成。

控制事件含version、id、replyTo、sessionId、type、body。id/requestId为UUID，字符串UTF-8，时间位置为整数毫秒，媒体采集时间为微秒。命令成功响应与状态事件分开，ack不等于首帧已显示。

示例（文档约定，非已实现API）：

```json
{"version":1,"id":"60ea52ce-5a55-4d46-900d-81224100bde3","type":"session.start","sessionId":null,"body":{"intent":"mirror","route":"dlna_live","deviceId":"local-device-id","profileId":"dlna-720p30","audioRequested":true}}
```

这是本机应用命令，不直接发送给DLNA电视。DLNA适配器转为UPnP控制；自有接收的远端WSS协议只携带它需要的协商/播放指令。

## 8. 自有远端控制与安全边界

使用WSS；自0.5.0 / 6起，各端统一采用强制配对协议v2，不保留旧发送端/旧接收端回退。mDNS必须包含当前pairingVersion和完整公开SPKI指纹，否则不进入设备列表；三端自动获取身份，不提供手填指纹的替代入口。一次性邀请为8位数字、120秒有效、最多五次尝试，并保留电视确认。TLS身份验证通过后，客户端先检查auth.challenge中的pairingVersion，再发送配对码；服务端在请求电视确认前检查pair.request版本，pair.accepted也必须回传版本。外层控制消息JSON的version仍为1，配对版本是独立合同，没有改变媒体消息封包格式。

二维码导入仍为后续目标，信任仅在当前进程/会话有效。iOS BroadcastTicket本地schema同步为2，拒绝旧格式配置。Android Legacy是旧系统/播放器适配，与软件旧版本兼容无关，仍使用相同的当前配对协议。

发现记录还必须携带监听端实际绑定的IPv4 `address`，并出现在DNS解析地址集合中；多网卡宿主不能随便取第一个地址。Apple宿主通过系统Bonjour浏览/发布，调用Rust listen时使用`advertise:false`，由原生发布器广播Rust返回的端口和公开身份；Android/其他Rust宿主使用内置mDNS。两种适配共享相同TXT与配对合同，不广播配对码。

挑战使用随机nonce、一次性有效期，签名绑定协议域、nonce、设备身份；采用成熟ECDSA/哈希库，不自行实现密码算法。服务发现不是授权。控制消息最大128KiB，SDP96KiB，ICE4096字节，队列最多32个待处理请求；拒绝重复JSON键、过深结构和无效类型。

远端消息集合：pair.request/accepted/rejected、session.start/accepted/stop、rtc.offer/answer/ice/state、file.load、playback.command、session.state、statistics、ping/pong、error。协商含negotiationId，旧ICE不得进入新会话。`replace-v1`恢复能力、父协商ID和仅本地的rtc.restart见[D10](12-RTC恢复与协商契约.md)；发送端本地rtc.state由恢复协调器消费，不向网络转发。错误至少区分权限、身份、媒体初始化、格式、网络、电视未拉流、慢接收与超时。

DLNA没有我们自有的WSS认证和SRTP；不要让其适配器伪造同等级安全状态。资源token/IP约束用于限制局域网访问，不应宣传成等同端到端加密。

## 9. 扩展与维护规则

1. 新平台实现CaptureConsent/Media/FilePlayer端口，领域与网络核心不添加平台条件分支。
2. 新协议增加独立适配器、能力描述、资源/控制映射和契约测试；不在每个UI按钮里判断协议名。
3. 新codec先扩展能力协商与媒体适配，再调整支持矩阵；旧客户端遇未知能力应忽略可选项、拒绝不支持的必需项。
4. 所有配置有schemaVersion和迁移测试；设备档案按型号/固件/配置失效，不靠散落品牌字符串判断。
5. 库类型不越过端口；更换播放器、HTTP栈或TS封装器时，只重写对应适配器与转换。
6. CI检查依赖方向、接口契约、各构建feature组合与禁用模块不被打包。v1采用编译期注册，不开放任意外部插件代码加载。
