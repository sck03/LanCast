# 04 平台实现与版本兼容

## 1. Android产品划分

Android自编业务统一Kotlin，首版Views/XML。不保留Java业务分支，不为了接入Java API而改选Java。产品构建分为三个逻辑App：

| App | 最低系统 | 依赖/能力 |
|---|---|---|
| Receiver Standard | Android6/API23 | libwebrtc接收、Media3 1.11.1、Rust控制；不带编码/TS封装功能 |
| Receiver Legacy | Android5/API21，主要覆盖21/22 | 相同控制/RTC协议、系统MediaPlayer、必要的受控loopback媒体桥 |
| Sender Android | Android10/API29 | 录屏/内部声音、RTC与DLNA直播发送、文件服务；不带电视播放器 |

Standard和Legacy共用业务和接口，播放器依赖分开。分版依据是平台/播放器维护边界，不代表高版本App会自动比同一硬件上的兼容版更快。降低minSdk本身不会降低新设备性能。

Legacy不设置maxSdkVersion；下载优先推荐Standard给API23+。Android4.x不支持。发布按ABI定向交付，区分产品变体和CPU架构包，详见构建文档。

## 2. Android发送端

流程：用户选来源与设备 → 必要的配对/兼容测试 → 点击开始 → 系统MediaProjection授权 → 合规前台服务 → 初始化CaptureSession → 对应媒体路由。

API29–33只承诺全屏；API34+使用系统单应用共享入口。裁剪桌面像素不等于安全独立的任意应用捕获，不能在旧系统提供无法兑现的任意App选择列表。

内部声音使用AudioPlaybackCaptureConfiguration，采允许的MEDIA/GAME/UNKNOWN等有效usage，按系统要求申请RECORD_AUDIO。应用可禁采，受保护内容可静音/黑屏；用户可明确选择静音继续或停止，不自动改为麦克风。

CaptureSession必须实现onStop、尺寸/方向变化、服务停止和进程退出清理。不要持久化或跨非法会话复用MediaProjection授权。网络恢复只能复用仍有效的当次捕获资源，不能偷偷重新获取系统权限。

视频用MediaCodec输入Surface和平台硬件H.264；音频PCM供选定的Opus/AAC消费者。同一个AudioRecord只有一个读取者，不让两个模块抢读；共享源需要明确的分发器，但首版一次只开一路，不引入无用的tee。

## 3. Android接收端

收到自有会话后先确认用户授权与设备能力，初始化成功再显示“已连接”。WebRTC和文件播放器互斥使用显示区域，切换必须释放前者。显示控件不能持有已销毁codec的Surface。

Standard播放器使用Media3 1.11.1，配受控HTTPS数据源；Legacy用系统MediaPlayer。旧播放器回调/seek精度/音频焦点不同，统一映射为FilePlayerPort事件，不把差异散落在UI。Legacy的TLS兼容由独立本机媒体桥解决，不关闭证书验证。

TV界面支持遥控器焦点、确认/拒绝、播放暂停、返回、音量和停止；不依赖触摸屏。前台活动期间保持屏幕亮，结束释放；v1.0不承诺在电视后台持续收屏。接收端不申请麦克风或MediaProjection权限。

硬件能力通过MediaCodecList/CodecCapabilities和实际初始化验证。API29+可用硬件标志辅助；旧系统codec名称只是线索。记录profile/level、尺寸、fps、色彩与已知驱动缺陷，不能只按Android版本选择1080p60。

## 4. Windows

Windows10 22H2/Windows11 x64，C++20 Win32界面，支持键盘导航、DPI与多显示器。界面仅调用应用用例，不在按钮事件里实现HTTP/UPnP/编码。

WGC提供整个显示器或窗口，D3D11完成必要的缩放/颜色转换，Media Foundation硬件MFT输出H.264。捕获源可高于输出分辨率，但输出4K/HDR不在首版；检测HDR源后按已验证SDR转换或说明限制，不默默产生错误色彩。

WASAPI loopback提供系统声音，监听默认输出设备变化并受控重建。单窗口画面仍可能配系统全局声音，UI必须分别标注。进程级音频隔离不是首版保证。

Windows N/缺少媒体组件、驱动不提供硬编、权限/受保护窗口等情况分别诊断。不通过GDI截图/JPEG轮询作为隐蔽备用方案，不直接采用一个包含所有codec的大型运行时解决初始化失败。

RTC桥和自定义编码器在libwebrtc固定工具链内编译，外部Win32层只使用C ABI；禁止混用不同编译器/STL构建的C++对象接口。TS封装是独立模块，不依赖GUI。

## 5. 中国受限电视

应用发现后展示具体能力：自有镜像、DLNA兼容镜像、文件播放、系统指引。禁止侧载/签名白名单/应用商店限制不能靠低minSdk解决。v1.0不包含Root、固件修改、签名绕过或强制ADB安装。

已有DLNA的受限电视可以尝试桌面直播，测试顺序先合成画面/提示音再真实屏幕；通过后保存配置档案。直播不兼容的设备仍可保留MP4直放。非Android系统如部分Tizen/webOS/VIDAA设备按协议能力接入，不能提供Android APK安装指引。

仅有系统AirPlay/Miracast时显示操作指引，不把系统完成的连接记成LanCast的媒体会话。无共同能力时需要外接接收盒子或未来OEM合作；不能把未达成的厂商合作写成现有能力。

## 6. 苹果平台

| 平台 | 安装与功能边界 |
|---|---|
| iPhone/iPad | 通常通过适用地区App Store或合法测试分发安装；企业/家长/地区限制可能阻止安装。不能安装Android APK |
| Apple TV HD/4K、tvOS | 需专门适配tvOS的App；不能安装任意iPhone App或Android APK。1.x不开发自有接收App |
| 旧Apple TV | 某些型号无App Store，不能推断能装新App |
| Mac | 需macOS适配；1.x不提供原生客户端 |

Apple TV内容App、Apple TV盒子/tvOS、AirPlay接收是不同概念。电视装了Apple TV内容App不自动拥有AirPlay，更不代表能接收WebRTC。Apple TV也不能被默认当作DLNA MediaRenderer。

v1.2 Swift宿主App+ReplayKit Broadcast Upload Extension。扩展独立处理采集、网络和停止，使用App Group只共享必要会话配置；不把原始录屏写成共享文件。方向、后台/扩展资源限制、受保护内容和声音策略都要实机测试。

iPhone系统“屏幕镜像”只连接相应AirPlay目标，不会发现仅提供WebRTC的自有接收端。走自有通道必须安装发送App并授权广播；将Windows DLNA直播移植到iOS也需要独立实现与验证。

## 7. 系统升级与兼容维护

minSdk、targetSdk和实际设备能力分别管理。固定targetSdk36用于首版构建；在更高系统版本上回归局域网权限、前台服务和native布局，不能靠低minSdk推断兼容所有未来版本。发布政策改变时按D04/构建决策流程升级。

每个受支持版本记录品牌/型号/固件/ABI/codec/网络/测试档位。旧机缺陷按版本化适配表处理，必要时禁用某个profile；不将厂商判断散落到所有媒体、UI和网络模块。
