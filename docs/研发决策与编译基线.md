# LanCast 1.x 研发决策与编译基线

决策日期：2026-10-03。本文是唯一产品/版本/编译选型基线。开发接口见[实现规格](实现规格.md)，设备边界见[设备接入与安装限制](设备接入与安装限制.md)，任务见[开发任务与验收](开发任务与验收.md)，依据见[对照调研](开源与商用品对照调研.md)。旧的重复方案已合并，不再并列维护。

**状态：设计确定；产品源码尚未实现。** 现有Java/API21接收、Rust服务与Windows浏览器原型已集中到 `prototype/`。Kotlin、Standard/Legacy、原生Windows、DLNA、生产配对和自建媒体库是下一阶段任务，不是已编译或已实机验收的功能。

## 1. 产品与协议决定

产品定位：**自有客户端提供完整镜像，DLNA视频发送覆盖部分不能安装App的电视**，局域网离线运行，单路投屏。中国电视禁止第三方安装是首版必须处理的场景，不能假定它们都能装接收APK。不建设通用AirPlay/Miracast/Cast接收器；系统已有能力通过明确的系统指引入口说明。

| 项目 | 固定决定 |
|---|---|
| 实时镜像 | WebRTC；视频 H.264，音频 Opus；LAN 点对点传输 |
| 视频直放 | 自有播放控制 + HTTP(S) Range；v1.0 必须支持 MP4/H.264/AAC |
| 应用层自有部分 | 发现、配对、设备能力、会话、控制指令、诊断、版本协商 |
| 不自研部分 | 编解码算法、RTP/SRTP、拥塞控制、抖动缓冲、底层密码算法 |
| 自有接收端 | Android 原生 App；运行发现与信令服务；手机投屏不依赖 PC 常开 |
| 外部协议 v1.0 | 实现DLNA/UPnP AV **发送控制器**，播放MP4到现有MediaRenderer；不模拟接收器，不用DLNA传桌面 |
| v1.1 | 设备兼容与质量维护，不预置新增通用协议接收栈 |
| AirPlay / Miracast | 1.x不实现协议栈；v1.0提供系统投屏指引，不显示虚构的LanCast连接/统计 |
| Google Cast | 1.x不实现发送/接收适配，提示用户使用已有官方Cast应用或其他支持路径 |
| HEVC / AV1 / HDR / 4K | 不在 v1.0 验收范围；不为它们增加第二套媒体引擎 |
| 多路拼屏、反向操控、云中转 | 不在 1.x 范围；一个接收端一次显示一条投屏 |
| iOS | v1.2 自有 Swift 发送 App + ReplayKit 广播扩展；不依赖系统 AirPlay 接收实现 |

“自有接收端”指自己控制 App 和会话，并不意味着重新发明媒体传输协议。只要网络和硬件允许，WebRTC 负责成熟的实时链路；自有 App 让捕获、编码协商、缓存、诊断与升级可统一管理。

不可安装App的电视：v1.0已有DLNA的可直接播放视频；已有Miracast/AirPlay的可按设备系统能力镜像，但不是LanCast托管的媒体链路。需要完整自有镜像时外接可安装LanCast的Android盒子。无共同协议、无安装渠道、无外接硬件时不承诺投屏。

iPhone/iPad通常通过App Store安装对应App，受地区/管理策略限制；Apple TV HD/4K上的tvOS App需要独立适配，不能安装Android APK或任意iPhone App。1.x不开发tvOS接收端；Apple TV原生AirPlay也不会接收自有WebRTC。v1.2 iPhone到我们的Android接收端需安装Swift发送App并授权ReplayKit广播。详见《设备接入与安装限制》。

## 2. 编程语言决定

| 模块 | 自编代码语言 | 实现边界 |
|---|---|---|
| Android 接收端、手机发送端 | **Kotlin** | 权限、生命周期、前台服务、TV UI、MediaProjection、AudioRecord、Media3、WebRTC Java API 调用 |
| 跨平台控制核心 | **Rust** | 发现、配对、会话、信令、能力规则、播放指令与本地诊断；不搬运每帧像素 |
| 媒体引擎及必要平台桥接 | **C++20**，复用 libwebrtc | 自定义音频采集入口、Windows 硬件编码接口、必要 JNI/C ABI；不重写 codec |
| Windows 客户端 | **C++20 原生 Win32 UI + Rust 核心** | Windows Graphics Capture、D3D11、WASAPI、Media Foundation；不用 Electron/WebView 作为产品采集容器 |
| Apple 发送端 v1.2 | **Swift**，薄 Objective-C++ 桥接 | ReplayKit 广播扩展、平台媒体与 native 库接入 |
| Go | 不采用 | 避免在 Rust 之外再维护一套相似的控制 runtime |
| Java | 仅保留上游接口与过渡源码 | 当前两份 Java 原型迁移为 Kotlin；不继续以 Java 扩写 Android 业务 |

选择 Kotlin 是因为 Android 的官方开发方向、空安全、生命周期集成与协程更适合持续维护。Kotlin 可直接调用 WebRTC 的 Java API，接入 libwebrtc 不要求业务代码使用 Java。Kotlin 与 Java 的区别不是本产品的主要视频性能变量，关键路径仍在 native 库、GPU 和硬件 codec。

Android UI 固定使用 Views/XML，先做遥控器焦点、配对、状态、设置四类页面；不引入 Compose 作为首版必需依赖。协程用于会话与任务管理，录音和视频渲染使用专用线程/库回调，避免逐帧对象分配与主线程拷贝。

## 3. Android发布物：能安装App时使用两个接收版本

| 发布物 | 系统范围与用途 | 播放器 | 媒体能力 |
|---|---|---|---|
| `LanCast Receiver Standard` | **Android6.0/API23+**；所有支持该版本的新旧电视默认使用 | **Media3 1.11.1** | H.264/Opus 镜像；MP4/H.264/AAC 直放；起步1080p30，满足硬件与网络条件才开1080p60 |
| `LanCast Receiver Legacy` | **minSdk21，主要面向 Android5.0/5.1/API21–22** | **Media3 1.8.1** | 同一 H.264/Opus 镜像协议与 MP4直放；起步720p30，验证通过的设备可升1080p30 |
| `LanCast Sender Android` | **Android10/API29+**；单独手机发送App | 不依赖电视播放器 | MediaProjection/允许的内部音频、MP4自有直放与DLNA发送；14+单应用分享 |

分版理由是已核实的播放器依赖分界，以及 Android5 驱动/播放行为需要独立维护。**不是用户强制两包，也不是系统版本越高就必须换一套更快的算法。** Standard 和 Legacy 共用 Kotlin业务、Rust控制、WebRTC媒体接口与线上的会话协议，不维护两个独立产品源码树。

Legacy 不设置 `maxSdkVersion`：Android 平台不适合用它阻止安装。下载入口对 API23+ 推荐 Standard，对 API21–22 推荐 Legacy；版本差异写入设备信息。为避免混装覆盖，应用 ID 分别为 `dev.lancast.receiver` 与 `dev.lancast.receiver.legacy`，构建变体为 `standard` 与 `legacy`。只有一个接收实例可以占用本机服务端口。

不为 CPU 架构再拆产品版本：两种接收 APK 都包含 armeabi-v7a、arm64-v8a；x86_64 只用于开发/模拟器构建。Android4.x不支持。Android5–9手机不进入发送 App 的 v1.0 支持范围，因为内部声音是核心功能；不会用偷偷录麦克风的方法补齐系统音频。

Legacy 进入 1.x 的维护范围，接受安全修复、崩溃和兼容修复；不跟进 Standard 后续新增的复杂视频格式。Media3 1.8.1 不被视为仍由上游持续维护：使用该旧版本意味着项目承担相关修复责任，受影响的已知严重问题未修复时不发布对应 Legacy 构建。两版的在线协议与发现信息继续兼容。

### WebRTC 的构建决定

1. 现有接收原型继续使用 `io.github.webrtc-sdk:android:150.7871.01` 做对照，不把现有 Java 编译结果移记到新工程。
2. 产品媒体库由源码构建：固定 `webrtc-sdk/webrtc` 提交 **0385653a83f21acf3c916466d4088b29fe2f160b**，建立项目补丁集。Android接收、Android发送与Windows使用同一源基线；不混用未经确认的预编译二进制和不同提交的 JNI。
3. Android内部声音补丁：给 Android AudioDeviceModule 增加显式的 `PlaybackCapture` 模式，使用授权的 `AudioPlaybackCaptureConfiguration` 创建 AudioRecord；保留其10ms分帧和采集时间传递。默认不启动麦克风；停止/撤销授权后关闭 AudioRecord。仅设置 `AudioBufferCallback` 不能完成这一功能。
4. Windows注入原生采集和编码实现：WGC提供GPU纹理；Media Foundation硬件H.264编码器实现 WebRTC VideoEncoder接口；WASAPI提供48kHz PCM给音频模块。只要需要软件编码降级，先降低画质，并明确显示状态。
5. WebRTC自身用 **GN/Ninja及该源码DEPS对应的工具链**构建；上表NDK/CMake用于项目的Rust/JNI桥，不能强制替换WebRTC的编译器和STL。跨库只开放受控C ABI/JNI，不传递STL容器。
6. native构建在Windows和Linux分别运行；Android自建AAR使用Linux构建机。将最终源提交、补丁哈希、实际DEPS revision、编译参数、ABI、库哈希写入构建清单。debug/release都验证16KB page-size相关要求。

当前没有已生成的产品自建AAR或完整native构建脚本。选择源码构建是为了明确解决Android内部音频和Windows硬编接入，不是声称预编译包已经提供这些全部能力。第一开发里程碑必须先把该构建与音频接口做通，再扩展UI与外部协议。

## 5. 数据通路、配对和状态机

**镜像通路：** 原生捕获 → 硬件H.264与Opus → WebRTC直连 → 原生解码与播放。手机端音频48kHz，按库接口分帧；视频与音频使用同一单调时间基准，由WebRTC做同步。默认不混麦克风声音，不对系统音频开启语音通话式AEC/降噪。

**视频直放：** 发送端本地文件服务提供带会话令牌的HTTP(S) Range URL；电视Media3拉流并负责同步。v1.0固定支持MP4/H.264/AAC及播放/暂停/seek/音量/停止；不做转码服务器、DRM网页解析、外挂字幕或HLS/DASH作为必须交付项。保留文件原编码避免录屏损失。

**发现与控制：** 接收端Rust核心托管服务；mDNS服务名 `_lancast._tcp`，提供手动IP兜底。生产控制用WSS；当前250ms HTTP轮询仅作原型。WebRTC不配置公网STUN/TURN；同LAN直连失败就说明网络隔离原因，v1.0不偷偷转公网中继。

**配对：** 新设备必须在电视确认。二维码携带接收端地址、一次性邀请和证书公钥指纹，客户端按指纹绑定TLS身份；PC手动连接使用电视显示的指纹核对流程。连接成功后保存设备公钥及授权，可在电视撤销。局域网中陌生设备不能仅凭“被发现”开始投屏；不使用关闭证书验证的方式上线。没有可信绑定时不发送SDP或媒体凭证。

状态机固定为 `Idle → Pairing → Negotiating → Streaming/Playing → Reconnecting → Stopped`。同一时间只允许一个活动会话，切换来源先征得接收端确认并关闭旧通路。断连恢复最多3次，退避1/2/4秒，总恢复窗口15秒，到期停止并清理采集、解码及令牌；授权被撤销立即停止，不自动重新请求授权。

## 6. 画质和首版验收

H.264为唯一必须支持的视频codec；协商profile/level，不只匹配MIME。Opus以48kHz为基础，音频采集条件不满足时明确提示，不能显示成正常有声投屏。

| 场景 | 默认起步 | 可开放上限 | 验收目标，尚未实测 |
|---|---|---|---|
| Legacy设备 | 720p30，约3Mbps | 通过设备测试后1080p30 | 稳定播放优先，镜像延迟p95≤350ms |
| Standard常规设备 | 1080p30，约6Mbps；能力不足降720p | 硬编硬解验证后1080p60，约10Mbps起步 | 1080p30镜像延迟p95≤200ms |
| 文件直放 | 保留源分辨率与编码 | 按接收codec能力限制 | 连续2小时无崩溃、正常seek及音画同步 |

音画偏移绝对值p95≤50ms；用测试片与外部摄像/采集设备测量，不能用RTT代替。码率由WebRTC拥塞控制调节；应用层遇持续5秒低帧率/解码积压降一个档位，持续30秒稳定且有足够带宽余量才升档。高版本Android也可能走720p，旧系统高性能硬件也不因包名被强制使用软件解码。

真机发布门槛：至少覆盖API21 ARM32低端投影、API22 ARM32盒子、API23/25电视、API28常规盒子、API30/34 ARM64与当前主流新Android。另必须包含不能安装第三方App但DLNA可用的中国电视及无共同协议的失败场景。两种接收版执行连接、声音、2小时长稳、尺寸变化、Wi-Fi切换/断连、权限撤销和内存回收测试。

## 7. 研发顺序与发布门槛

| 顺序 | 明确交付 | 未满足时的处理 |
|---|---|---|
| M0：工程与媒体可构建 | Kotlin迁移；两个接收变体与手机发送模块；自建WebRTC；Windows硬编与Android内部声音样例 | 不进入功能堆叠，不以默认麦克风音轨冒充系统音频 |
| M1：实时链路闭环 | Windows/Android10+ → 两种接收版；配对、发现、重连、同步和质量统计 | 修复对应设备/链路，不加入外部协议掩盖问题 |
| M2：v1.0 | MP4自有直放及DLNA发送；受限电视路由；权限/可信配对及既定设备验收 | 必须含禁止安装App但DLNA可用的实机；DLNA故障不能拖垮自有会话 |
