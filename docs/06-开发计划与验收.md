# 06 开发计划与验收

实施已开始，当前状态见08。以下仍是v1.0退出门槛；源码、编译通过或模拟测试不能替代真机门槛。

## 1. 实施顺序

| 阶段 | 依赖 | 必须交付 | 退出条件 |
|---|---|---|---|
| M0 工程与接口 | 文档基线 | 四层模块、组合入口、版本化端口/C ABI、固定依赖清单 | 依赖方向检查、接口生命周期测试、各角色空运行，不初始化无用媒体 |
| M1 媒体基础 | M0 | D08的RTC输入、Windows/Android硬件H.264、合法声音源、最小TS封装 | 固定源码/二进制输入可追溯，真实编码样本/时间戳正确，库/ABI/许可清单完整；Android定制源构建状态单列 |
| M2 自有镜像 | M1 | WSS配对、RTC、TV接收、授权/停止、基本统计 | Windows和Android到Standard/Legacy均通过真实音视频及资源释放 |
| M3 DLNA直播服务 | M0/M1 | SSDP/UPnP、TS缓存、HTTP发布、完整起播点、慢读处理 | 合成TS→模拟渲染器闭环，格式/状态/故障测试通过 |
| M4 受限电视直播 | M3 | Windows和Android采集接入、ReceiverProfile、用户Probe | 实际禁止安装App的电视成功播放桌面/PPT与声音，完成延迟分级 |
| M5 文件播放 | M0/M1 | 原文件服务、Media3/System MediaPlayer、Legacy媒体桥、DLNA文件 | Range/seek/认证/撤销通过，文件与直播控制不混用 |
| M6 质量与恢复 | M2/M4/M5 | 真实统计驱动画质、有限重连、源切换、设备档案 | 不无限积压/重播，不伪报已应用参数；权限撤销立即结束 |
| M7 发布 | 所有前置 | 单ABI包、签名、SBOM、诊断、更新/回退、支持矩阵 | 三条通路分别验收，无被藏在“以后研究”里的首版必需项 |

M1尽早在目标低端设备验证，不在完成全部UI后才发现硬件路径不能工作。M3用合成内容验证网络/封装，与真实用户录屏分开。M4不能仅凭电脑上的MockRenderer通过便宣布完成。

苹果发送与接收已按新增需求提前实施，架构和独立验收见D09。后续版本维护真实兼容、恢复和质量问题；新增协议按端口适配与独立验收，不在平台UI里追加大量协议分支。

## 2. 架构和契约验收

- 领域层没有网络、UI或媒体库依赖；平台适配没有反向调用其他平台模块。
- 更换模拟播放器/发现/传输实现时，业务核心测试不需修改。
- public类型不暴露第三方对象、STL容器、Rust引用或Kotlin对象。
- ABI带版本/长度；回调生命周期、shutdown、重复stop、失效handle、背压均有契约测试。
- RoutePlan覆盖：自有优先、DLNA直播passed/unknown/failed、文件passed但直播未知、本端后端缺失、系统指引、无可用路径。
- 设备证据不能绕过授权；use/probe都不是自动开始捕获的许可。
- 角色feature依赖图无编码/TS库泄漏到接收端，无播放器泄漏到发送端。
- 修改协议字段、存储schema或错误码时，升级与兼容行为有测试与决策记录。

## 3. 媒体与网络自动化

| 范围 | 核心场景 |
|---|---|
| RTC | SDP前ICE、方向/来源变化、失效negotiation、音轨有无、停止、有限重连 |
| TS | 包同步、PAT/PMT、SPS/PPS/IDR、分块NAL/PES、PTS与交织、关键帧间隔、坏流拒绝 |
| 直播缓冲 | 新GET从合法起点、慢读者隔离、字节/时长双上限、无任意P帧丢弃、撤销即时生效 |
| HTTP直播 | chunked/close-delimited分别验证、HEAD、Range策略、无假长度、token/IP限制 |
| HTTP文件 | 200/206/416、首尾/越界/空文件、多段Range策略、只读资源、取消和授权 |
| UPnP | service版本、UDN一致性、相对URL、SSRF/DTD、SOAP fault、写超时后先查状态 |
| 身份 | SPKI绑定、邀请有效期/次数、挑战重放、电视拒绝、日志脱敏 |
| 生命周期 | 阻塞录音解除、线程退出、迟到回调、源关闭、UI离开、进程结束 |

合成时钟画面、提示音和可重复视频样本优先，不把真实用户桌面作为自动化采集素材。解析/传输验证不等于可听同步或电视显示验证。

## 4. 必须的真机矩阵

1. Legacy API21与22 ARM32盒子/投影，至少一台低性能设备。
2. Standard API23/25/28及较新的ARM64电视，验证硬解/播放器/音频。
3. Android发送API29与API34+，分别测试允许/禁止采集声音、全屏/单应用与撤销。
4. Windows10 22H2与Windows11 x64，至少两类GPU/驱动；缺媒体组件或硬编不可用失败场景。
5. 至少一台不能安装第三方App但连续DLNA直播可用的中国电视，并有另一独立渲染器样本。
6. MP4可播但TS直播失败或预缓冲很大的设备，确保准确降级和提示。
7. Wi-Fi/以太网、AP隔离、网络切换、带宽下降、接收器关机/停止。
8. 无共同协议、非Android电视及iPhone/Apple TV安装说明的正确性检查。
9. D09的Mac Intel/Apple Silicon、iPhone/iPad广播扩展、Apple TV遥控/声音与Windows/Android双向互通；签名、后台、旋转、系统撤销、重复文件播放。

记录品牌、型号、固件、ABI、codec/profile、分辨率/fps、网络、HTTP模式、构建版本与失败原因。不能只记录“某品牌通过”。

## 5. 性能与质量目标

以下均为项目验收目标，尚未测得：

| 通路 | 基准场景 | 目标 |
|---|---|---|
| WebRTC Standard | 健康LAN、硬编硬解1080p30 | 画面端到端延迟p95≤200ms，音画偏移绝对值p95≤50ms |
| WebRTC Legacy | 健康LAN、720p30 | 延迟p95≤350ms，音画偏移目标≤50ms |
| DLNA桌面直播 | 720p30，真实电视 | p95≤1秒标较低延迟兼容档；1–3秒标演示档；>3秒标高延迟、不默认推荐交互 |
| DLNA声音 | 有声测试片 | 音画偏移绝对值p95目标≤80ms；未测显示未知 |
| 长稳 | 各必须通路 | 探索阶段30分钟，发布阶段2小时，无崩溃/持续积压；停止后资源回收 |

用同帧闪光/点击声、外部摄像或采集卡测量；RTT、GOP、缓冲长度、SOAP PLAYING不是画面延迟。记录p50/p95、最差现象及环境，不用平均值掩盖卡顿。

对不支持TS直播的电视标记unsupported并保留可用文件模式，这不是测试失败后篡改目标。至少一台实际受限电视完成直播验收，才可宣布首版这条路线交付。

## 6. 维护和扩展验收

每个模块有负责人、公开接口、错误表、契约样本和回归入口。缺陷先定位采集/编码/传输/接收/显示层，不用“网络差”统一解释。设备规避项有适用版本和移除条件。

新增依赖必须说明用途、替代方案、包体增量、许可证、平台/ABI支持和更新策略。每次升级走独立变更，更新锁文件/构建清单/设备回归，不混入业务功能提交。

功能从实验到发布的门槛是实现、自动化、实机、文档四项同时完成。运行时不能通过一个隐藏开关把未实现/未验证的路线伪装成已支持。

## 7. D15按需AirPlay接收专项

[D15](18-AirPlay按需接收设计与接入方案.md)的0.6.0实现采用修正后的rairplay，包含现代/旧配对入口、加密媒体、Android宿主与独立产品构建。源码和自动化范围见[20](20-AirPlay实现与审阅指南.md)，实际结果见[08](08-实施进度与审阅入口.md)。该通路独立验收，不能用已有通路、其他产品、模拟客户端或仅legacy成功替代现代AP2真机目标。

| 阶段 | 交付与退出条件 |
|---|---|
| A0 协议优先级与独立原型 | 优先验证rairplay等现代AP2候选，并对照UxPlay与CastBay/android-airplay-server的旧镜像配置；核查完整协议/媒体接口、生产密钥、依赖/分发、父工程与子模块，先分别证明两种模式 |
| A1 前台接收闭环 | 在真实苹果与Android设备上分别完成现代AP2和目标旧模式的配对、画面及伴随声音；验证双方支持时AP2优先、旧端使用兼容配置；错误分类、协商/显示等待有上限 |
| A2 手动开关与服务 | 默认关闭；手动启用后Home后台监听；页面重建不重复启动；关闭撤销发现并释放全部AirPlay资源；无开机启动和进程结束后的自动恢复 |
| A3 互斥、兼容与显示边界 | 单路仲裁、后台播放页与有限等待分别验证；兼容重试仅在另有已验证的镜像配置且满足D15第6.2节时启用，无第二配置时明确结束失败连接并提示重连 |
| A4 兼容与发布 | 固定依赖、各ABI构建/包体、开启/关闭模块组合、系统/机型矩阵、长稳、诊断、分发材料及用户说明全部通过 |

自动化覆盖：连续开关、重复stop、启动中关闭、旧代次回调、启用失败清理、页面重建、服务异常结束、网络断开/切换/恢复、配对取消、接入冲突、Surface丢失、媒体队列背压和清理屏障。模拟协议事件只验证宿主合同；仅mDNS可见或握手成功不能作为镜像通过。

兼容策略另验：明确的版本/能力不兼容与未知错误分流；PIN/身份/签名/完整性/密钥错误不得触发自动降级；网络超时不改协议配置；没有备用镜像实现时不提供虚假回退；一次尝试最多一次兼容重试且重连共享预算、关闭会取消重试。调节发现能力前检查无活动/待确认会话；新连接不复用旧密钥、旧代次或放宽接入确认。

参考工程适配另验：父工程/子模块成组固定；没有带入开机广播、`START_STICKY`、默认关闭PIN或固定开发密钥；裁剪额外功能后仍可完整镜像。CastBay的API23、android-airplay-server的API24和PhairPlay的API25/29不能直接作为本项目全部Standard/Legacy已支持的证据；不自动继承compileSdk37等工具链。许可/源码清单追溯到原生PlayFair等组件。

真机验收必须覆盖：

1. iPhone与iPad各至少一台，至少两个实际可获得的系统版本，包含拟支持的最新版本及较旧版本；手机不安装LanCast发送App，从系统“屏幕镜像”进入。记录系统、引擎版本、实际握手/镜像模式和发现能力，至少分别取得现代AP2与目标旧模式的画面/声音证据；D09最低系统和上游记录不自动成为本通路承诺。
2. Standard至少一台较新API34+设备和一台较旧API23–28设备，涵盖目标ARM ABI；Legacy API21/22另行验证，未通过的变体不开放可用开关。平台版本、targetSdk、服务类型和前台启动条件随证据记录。
3. 开关关闭时无本应用AirPlay主动响应/监听；开启成功后可发现并实际显示、发声；手机列表的旧缓存与仍在运行的服务分开判断。
4. Home后至少30分钟待机、再从手机发起连接；接收页可见、可从后台打开、被系统限制后台打开三类情况分别记录。通知被关闭或电视无可操作通知入口时，验证手动打开接收页后可重新连接。
5. 手机断开后继续等待；播放页返回仅停止当前投屏；首页退出/手动关闭结束服务；强行停止App、服务/进程结束和电视重启后不自动恢复AirPlay。
6. 实际镜像画面与伴随声音、横竖屏/分辨率变化、无音轨与不支持音频配置、网络故障、配对取消/超时、两个发送源争用；不把DRM黑屏作为可通过协议兼容解除的条件。
7. 探索阶段30分钟播放、发布阶段2小时播放；重复启停后线程、套接字、锁、解码器和音频焦点回收，无持续增长。记录关闭、启用待机、播放三个状态的CPU/RSS/包体及实际延迟/音画同步，不沿用WebRTC性能结论。
8. 仅在备用镜像配置实际存在时测试受控重连，记录iOS是否自动重连、是否需用户重新选择、是否仍有画面与伴随声音。不能用RTSP连接成功或仅音频播放作为“AirPlay 1镜像降级成功”的证据；未证明可自动重连的组合使用手动重连说明。

0.6.0已进入实现/自动化阶段：真实套接字覆盖现代SRP/配对/加密控制、错误PIN、旧配对签名校验、失败不降级、NTP下H.264与音频编码数据交付以及关闭中断；纯Kotlin测试覆盖互斥租约、旧代次与队列边界。Android服务生命周期、系统发现、实际解码/可听同步与完整机型矩阵仍按上述清单实测，不把协议回环当作A1/A4完成。

## 8. D17媒体队列与资源维护

0.6.2的实现合同见[21](21-AirPlay媒体队列与资源生命周期.md)。自动化须验证配置消息不能隐藏时长预算、乱序/重复时间戳与出队恢复、字节/帧数/整数边界、等待超时与中断、关闭唤醒及并发入队；资源初始化在成功/部分失败/释放失败三种情况下有明确所有权。Android产品构建按配置执行这些JVM测试并保留报告。

设备验收在D15清单上增加：缺少音轨时的空闲线程、反复格式变化及解码器启动失败后的资源数量，AAC/PCM直接输出与停止时缓冲归还、音频焦点中断。记录启停前后线程、解码器/AudioTrack、CPU/RSS/分配、真实可听同步；JVM替身测试通过不等同平台资源和性能验收完成。

## 9. D18 HTTP生命周期与直播分发

自动化覆盖正常请求结束取消、连续连接回收、四连接上限及名额复用、监听停止/中止清理、稳定直播共享同一数据分配、起播超时、过时媒体拒绝、等待中撤销和迟到订阅。保留文件Range/HEAD/TLS固定身份回环与真实合成TS的HTTP/1.0、HTTP/1.1解码验证。执行与结果见[22](22-HTTP生命周期与直播分发.md)和08。

实机补测连续文件seek、慢电视断连重拉、局域网切换及重复停止/启动，记录连接/句柄数量和CPU/RSS，确认稳定播放与声音。内存地址共享测试只证明消除了指定复制，不能替代端到端延迟、RSS或两小时长稳测量。
